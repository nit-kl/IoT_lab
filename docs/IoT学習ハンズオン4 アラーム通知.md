# IoT学習ハンズオン4:アラーム通知

Oct 15, 2026 · @Reo Kojima

前提:[IoT学習ハンズオン3 Lambda+DynamoDBで最新値を持つ](./IoT学習ハンズオン3%20Lambda%2BDynamoDB最新値.md)が終わっていて、`python aws/show_latest.py` で最新値が見えることです。所要時間は60〜90分です。費用は数時間の学習なら1円未満、ゲートウェイを1か月つけっぱなしにしても追加は月百円程度です(詳しくは最後の「費用」)。

## 全体像

ハンズオン3で作った最新値テーブルは「店舗の今の状態」を持っています。今回はその**変化**を拾い、異常が起きたとき・直ったときにメールを送ります。

スーパーで一番大事な通知は、**冷蔵ショーケースの温度逸脱**です。HACCPに沿った衛生管理では、冷蔵品は10℃以下で保つことが求められます。扉の閉め忘れや冷凍機の故障で庫内温度が上がると、気づくのが遅れるほど廃棄が増えます。夜間や閉店後は売場に人がいないので、自動の通知が必要です。

```
最新値テーブル ──(DynamoDB Streams: 変更前と変更後)──┐
                                                       ├─→ 通知Lambda ──→ SNS ──→ メール
EventBridge Scheduler(1分ごと: 途絶チェック)─────────┘        │
                                                               └─→ 状態テーブル(通知済みの異常)
```

| 追加するもの | 役割 | 学べること |
| --- | --- | --- |
| 最新値テーブルの StreamSpecification | 行が変わるたびに「変更前・変更後」をストリームに流す | 変化(イベント)を拾う設計。全件を定期的に見に行かなくてよい |
| aws/lambda/alarm\_notifier.py | 異常の発生・復旧を判定して通知 | オンディレイ(瞬時異常の除外)、霜取り中の除外、状態の変化でだけ通知 |
| AlarmStateTable | 通知済みで未復旧の異常を1件1行で持つ | 条件付き書き込みで「同じ異常で何通も送らない」 |
| AlarmTopic(SNS) | メール配信 | 通知先の追加・変更をコードから切り離す |
| StaleCheckSchedule | 1分ごとに通知Lambdaを起動 | 「データが来ない」は受け手が時刻で判断する |
| simulator/force\_alarm.py | シミュレータに異常や扉の開けっ放しを起こすテスト用ツール | 試験のために異常を再現できるようにしておく |

通知する異常は4種類です。

| 種類 | 対象 | 発生の条件 | 復旧の条件 |
| --- | --- | --- | --- |
| 温度逸脱 | 冷蔵ショーケース(case\_temp\_c がある機器) | 庫内温度が上限(10℃)を超え、霜取り中でない状態が**2回続いた** | 庫内温度が上限以下に下がった |
| 異常コード | 全機器(alarm\_code がある機器) | 異常コードが0以外で**2回続いた** | 異常コードが0に戻った |
| 通信エラー | 全機器 | comm\_error が**2回続いた** | ok に戻った |
| データ途絶 | 全機器 | 最後のデータから120秒以上たった(1分ごとに確認) | データがまた届いた |

## 通知の設計で押さえること

運用の現場で一番嫌われるのは「鳴りすぎる通知」です。鳴りすぎると誰も見なくなり、本当の異常を見落とします。店舗の場合、通知を受けるのは店長や夜間の警備、本部の設備担当です。夜中に意味のない通知で起こされることが続くと、通知を切られてしまいます。今回のLambdaは次のルールで通知を絞っています。

| ルール | 内容 | 仕組み |
| --- | --- | --- |
| オンディレイ | **2回続けて**(約10秒以上)異常だったら通知。1回だけの異常は通知しない | Streamsの変更前(OldImage)と変更後(NewImage)の両方が異常かを見る |
| 霜取り中は温度逸脱としない | 霜取り中(defrost=1)は庫内温度が上がるのが正常なので、上限を超えても数えない | 判定の関数 hot() で、defrost が1なら異常としない |
| 状態の変化でだけ通知 | 異常が続いている間は再通知しない。直ったら1回だけ「復旧」を送る | 状態テーブルに `attribute_not_exists(pk)` の条件付きで書けたときだけ送る |
| 通知していない異常の復旧は送らない | 一瞬だけの異常は、発生も復旧も送らない | 状態テーブルに行があるときだけ消せる(`attribute_exists(pk)`)。消せたら復旧通知 |

**霜取りとは**:冷蔵ショーケースは、冷却器に付いた霜を溶かすために、数時間おきに冷却を止めます(霜取り、デフロスト)。その間、庫内温度は一時的に上がります。シミュレータでは学習用に、8分ごとに90秒の霜取りをします。霜取り中は庫内温度が12〜13℃まで上がり、10秒ごとの読み取りで6回ほど上限を超えます。霜取り中を除外しないと、8分ごとに温度逸脱のメールが届くことになります。霜取りが終わると数秒で10℃以下に戻るので、霜取り直後に1回だけ上限を超えた値が読めても、オンディレイで除外されます。

**温度の上限はどこで決めるか**:上限(10℃)は template.yaml の通知Lambdaの環境変数 `TEMP_MAX_C` にあります。実際の店舗では、売り場や商品(鮮魚・精肉・日配・飲料)ごとに上限が違うので、機器ごとの上限をポイントリストや設備台帳で管理し、Lambdaはそれを読む形にします。

シミュレータは約1%の確率で異常コード(売場空調101、冷凍機盤3021)を**一瞬だけ**出します。ハンズオン1のクエリ7で件数が見えていたものです。これらはオンディレイで除外されるので、メールは来ません。

**なぜ状態テーブルが要るのか**:Streamsは「最新値テーブルの行が変わった」ことしか教えてくれません。「この異常はもう通知したか」は別に覚えておく必要があります。ここでもハンズオン3と同じ条件付き書き込みを使います。Lambdaが失敗して同じレコードで再実行されても、2通目は送られません。

**送信に失敗したら**:状態テーブルに書いた後でSNSの送信に失敗すると、「通知済み」と記録されたまま誰にも届かない状態になります。そこで、送信に失敗したら状態テーブルの行を消してから例外を出し、Streamsの再試行で送り直します。

**再試行の上限**:Streamsのトリガーは、既定では失敗したレコードを(最大24時間)延々と再試行し、その後ろのレコードがすべて止まります。template.yaml では `MaximumRetryAttempts: 3` として、3回で諦めるようにしています。

**データ途絶はStreamsでは分からない**:ゲートウェイが止まると最新値テーブルへの書き込みが無くなるので、Streamsには何も流れません。「来ないこと」を知るには、別の仕組みで定期的に時刻を確認する必要があります。そのため、EventBridge Scheduler で1分ごとに通知Lambdaを起動し、`ts` が120秒以上古い機器を「データ途絶」として通知します(ハンズオン3の show\_latest.py の STALE と同じ考え方を自動化したものです)。店舗では停電やゲートウェイの電源抜けで起きます。

## ステップ1:AWS環境を更新し、通知先を登録する

1. 前回までと同じく仮想環境を有効にし、`--email` に自分のメールアドレスを付けて `setup_aws.py` を再実行します(1〜3分)。

   ```
   python aws/setup_aws.py --email you@example.com
   ```

   最後に次の行が出ます(kojima の部分は自分の owner)。

   ```
   通知先 you@example.com を登録しました。届いた確認メールの「Confirm subscription」を押してください
   通知Lambdaのログ: aws logs tail /xcp/store-iot/kojima/alarm-notifier --follow
   ```
2. 「AWS Notification - Subscription Confirmation」というメールが届くので、本文の **Confirm subscription** を押します。押すまでは通知が届きません。迷惑メールフォルダに入っていることがあります。
3. シミュレータ(run\_store.py)とゲートウェイを、ハンズオン3と同じように動かします。別のターミナルで通知Lambdaのログを流しておくと、何が起きているか分かりやすくなります(コマンドは `setup_aws.py` の最後に表示されたものをコピー)。

## ステップ2:ショーケースの扉を開けっ放しにして通知を受け取る

1. 冷蔵ショーケース RC-01 の扉を開けっ放しにします(品出しの後に扉が半開きのまま、という想定です)。

   ```
   python simulator/force_alarm.py --door open
   ```
2. `python aws/show_latest.py --watch 5` で、RC-01 の door\_open=1 になり、case\_temp\_c が少しずつ上がっていくのを見ます。30秒ほどで10℃を超えます。
3. 10℃を超えてから20〜30秒ほどで「[発生] RC-01 庫内温度 11.5℃(上限 10℃)」のようなメールが届きます。ゲートウェイが10秒ごとに読み、2回続けて上限を超えたときに通知するためです。
4. 開けたまま1〜2分待ちます。温度は上がり続けますが、**2通目は来ません**(状態の変化でだけ通知するため)。
5. 扉を閉めます。

   ```
   python simulator/force_alarm.py --door close
   ```

   数十秒で庫内温度が10℃以下に戻り、「[復旧] RC-01 庫内温度 …」が届きます。本文に発生時刻と復旧時刻(日本時間)が入っています。HACCPの記録では、この「いつからいつまで逸脱していたか」と「何をしたか(扉を閉めた)」を残すことが求められます。

## ステップ3:設備の異常コードで通知を受け取る

1. 売場空調に異常コード201を発生させます。

   ```
   python simulator/force_alarm.py --code 201
   ```
2. 20〜30秒ほどで「[発生] AC-01 異常コード 201」というメールが届きます。
3. 解除します。

   ```
   python simulator/force_alarm.py --code 0
   ```

   10〜20秒ほどで「[復旧] AC-01 異常コード 201」が届きます。ショーケースの異常コードは `--target RC-01` を付けると同じように試せます。

## ステップ4:やってみる

| 実験 | 操作 | 期待される結果 |
| --- | --- | --- |
| 霜取り | 何もせず、show\_latest.py で RC-01 を8分以上見る | defrost=1 の間は case\_temp\_c が12℃前後まで上がるが、メールは来ない |
| 瞬時異常 | `python simulator/force_alarm.py --code 202 --pulse 3`(3秒だけ異常にして自動で解除) | メールは来ない。show\_latest.py や Athena で alarm\_code=202 の行が見えることはあるが、1回だけなのでオンディレイで除外される |
| 扉をすぐ閉める | `python simulator/force_alarm.py --door open --pulse 20`(20秒だけ開ける) | 庫内温度は上がるが10℃に届く前に戻るので、メールは来ない |
| 通信エラー | `python simulator/run_store.py --except RC-01` と `python simulator/showcase.py` で起動しておき、showcase.py だけを Ctrl+C で止める。30秒待つ | RC-01 の「[発生] 通信エラー」だけが届く(1台だけの故障)。showcase.py を再起動すると「[復旧]」が届く |
| データ途絶 | ゲートウェイをCtrl+Cで止め、3〜4分待つ | 4台分の「[発生] データ途絶」が届く(120秒+チェック間隔1分)。ゲートウェイを再起動すると、1分以内に4台分の「[復旧]」が届く |
| 状態テーブルを見る | 扉を開けたまま、DynamoDBコンソールで xcp-store-iot-kojima-alarm-state の項目を見る | `RC-01#temp` の行がある。復旧すると消える。「通知済みで未復旧の異常」の一覧そのもの |
| しきい値を変える | template.yaml の `STALE_SEC: '120'` を `'60'` に変えて `setup_aws.py` を再実行し、データ途絶を試す | 通知が早くなる。短すぎると一時的な遅れでも鳴ることを考えて決める値 |

**やってみる(コード変更)**:`aws/lambda/alarm_notifier.py` の hot() の `and not m.get("defrost")` を消して `setup_aws.py` を再実行すると、霜取り中の除外が無くなります。8分ごとに温度逸脱のメールが届くようになることを確認してから元に戻してください。「通知が鳴りすぎる」状態の体験です。同じように、on\_change の中の `if code and prev:` を `if code:` に変えると、オンディレイが無くなり、シミュレータの一瞬の異常(101や3021)でもメールが来るようになります。

## 片付け

```
python aws/teardown_aws.py
```

SNSトピック・購読・Lambda・スケジュールもスタックごと削除されます。

**注意**:学習を中断してゲートウェイを止めると、数分後に「データ途絶」のメールが4通届きます。異常ではなく仕様どおりの動きです。スタックを残したままメールを止めたい場合は、届いたメールの末尾の「unsubscribe」リンクで購読を解除します(再開時は `--email` を付けて `setup_aws.py` を再実行すれば登録し直せます)。

## よくあるつまずき

| 症状 | 原因と対処 |
| --- | --- |
| メールが1通も来ない | 確認メールの Confirm subscription を押していない。SNSコンソールのサブスクリプションで状態が「確認済み」か確認する。迷惑メールフォルダも見る |
| force\_alarm.py が「接続できません」 | 書き込み先の機器のシミュレータが動いていない(run\_store.py、または個別に起動した aircon.py / showcase.py) |
| 扉を開けても温度逸脱のメールが来ない | 霜取りと重なった可能性。霜取り中は判定しないので、霜取りが終わってから2回続けて上限を超えると届く |
| 「[発生]」は来たが「[復旧]」が来ない | ゲートウェイが止まっている(復旧も最新値の変化で判定するため)。ゲートウェイを動かす |
| ゲートウェイを止めていないのに「データ途絶」が来る | PCの時計がずれている。Windowsの「設定 → 時刻と言語 → 今すぐ同期」 |
| 通知Lambdaのログに `KeyError: 'TEMP_MAX_C'` | template.yaml が古い。最新の template.yaml で `setup_aws.py` を再実行する |
| 通知Lambdaのログに `AccessDeniedException` | template.yaml の AlarmNotifierRole を書き換えた場合は、対象のテーブル・トピックと操作が合っているか確認 |
