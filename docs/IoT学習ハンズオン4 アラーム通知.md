# IoT学習ハンズオン4:アラーム通知

Oct 12, 2026 · @Reo Kojima

前提:[IoT学習ハンズオン3 Lambda+DynamoDBで最新値を持つ](./IoT学習ハンズオン3%20Lambda%2BDynamoDB最新値.md)が終わっていて、`python aws/show_latest.py` で最新値が見えることです。所要時間は60〜90分です。費用は数時間の学習なら1円未満、ゲートウェイを1か月つけっぱなしにしても追加は月数十円程度です(詳しくは最後の「費用」)。

## 全体像

ハンズオン3で作った最新値テーブルは「今の状態」を持っています。今回はその**変化**を拾い、異常が起きたとき・直ったときにメールを送ります。

```
最新値テーブル ──(DynamoDB Streams: 変更前と変更後)──┐
                                                       ├─→ 通知Lambda ──→ SNS ──→ メール
EventBridge Scheduler(1分ごと: 途絶チェック)─────────┘        │
                                                               └─→ 状態テーブル(通知済みの異常)
```

| 追加するもの | 役割 | 学べること |
| --- | --- | --- |
| 最新値テーブルの StreamSpecification | 行が変わるたびに「変更前・変更後」をストリームに流す | 変化(イベント)を拾う設計。全件を定期的に見に行かなくてよい |
| aws/lambda/alarm_notifier.py | 異常の発生・復旧を判定して通知 | オンディレイ(瞬時異常の除外)、状態の変化でだけ通知 |
| AlarmStateTable | 通知済みで未復旧の異常を1件1行で持つ | 条件付き書き込みで「同じ異常で何通も送らない」 |
| AlarmTopic(SNS) | メール配信 | 通知先の追加・変更をコードから切り離す |
| StaleCheckSchedule | 1分ごとに通知Lambdaを起動 | 「データが来ない」は受け手が時刻で判断する |
| simulator/force_alarm.py | シミュレータに異常を起こすテスト用ツール | 試験のために異常を再現できるようにしておく |

## 通知の設計で押さえること

運用の現場で一番嫌われるのは「鳴りすぎる通知」です。鳴りすぎると誰も見なくなり、本当の異常を見落とします。今回のLambdaは次の4つのルールで通知を絞っています。

| ルール | 内容 | 仕組み |
| --- | --- | --- |
| オンディレイ | 異常コードが**2回続けて**(約10秒以上)出たら通知。1回だけの異常は通知しない | Streamsの変更前(OldImage)と変更後(NewImage)の両方が異常かを見る |
| 状態の変化でだけ通知 | 異常が続いている間は再通知しない。直ったら1回だけ「復旧」を送る | 状態テーブルに `attribute_not_exists(pk)` の条件付きで書けたときだけ送る |
| 通知していない異常の復旧は送らない | 一瞬だけの異常は、発生も復旧も送らない | 状態テーブルに行があるときだけ消せる(`attribute_exists(pk)`)。消せたら復旧通知 |
| 通信エラーも同じ扱い | comm_error が2回続いたら「通信エラー」、ok に戻ったら「復旧」 | 同上 |

シミュレータは約1%の確率で異常コード(空調機101、iQ-R 3021)を**一瞬だけ**出します。ハンズオン1のクエリ7で件数が見えていたものです。これらはオンディレイで除外されるので、メールは来ません。

**なぜ状態テーブルが要るのか**:Streamsは「最新値テーブルの行が変わった」ことしか教えてくれません。「この異常はもう通知したか」は別に覚えておく必要があります。ここでもハンズオン3と同じ条件付き書き込みを使います。Lambdaが失敗して同じレコードで再実行されても、2通目は送られません。

**送信に失敗したら**:状態テーブルに書いた後でSNSの送信に失敗すると、「通知済み」と記録されたまま誰にも届かない状態になります。そこで、送信に失敗したら状態テーブルの行を消してから例外を出し、Streamsの再試行で送り直します。

**再試行の上限**:Streamsのトリガーは、既定では失敗したレコードを(最大24時間)延々と再試行し、その後ろのレコードがすべて止まります。template.yaml では `MaximumRetryAttempts: 3` として、3回で諦めるようにしています。

**データ途絶はStreamsでは分からない**:ゲートウェイが止まると最新値テーブルへの書き込みが無くなるので、Streamsには何も流れません。「来ないこと」を知るには、別の仕組みで定期的に時刻を確認する必要があります。そのため、EventBridge Scheduler で1分ごとに通知Lambdaを起動し、`ts` が120秒以上古い機器を「データ途絶」として通知します(ハンズオン3の show_latest.py の STALE と同じ考え方を自動化したものです)。

## ステップ1:AWS環境を更新し、通知先を登録する

1. 前回までと同じく仮想環境を有効にし、`--email` に自分のメールアドレスを付けて `setup_aws.py` を再実行します(1〜3分)。

   ```
   python aws/setup_aws.py --email you@example.com
   ```

   最後に次の行が出ます。

   ```
   通知先 you@example.com を登録しました。届いた確認メールの「Confirm subscription」を押してください
   通知Lambdaのログ: aws logs tail iot-lab-AlarmNotifierLogGroup-XXXXXXXX --follow
   ```
2. 「AWS Notification - Subscription Confirmation」というメールが届くので、本文の **Confirm subscription** を押します。押すまでは通知が届きません。迷惑メールフォルダに入っていることがあります。
3. 新しいシミュレータの機能(強制異常)を使うため、**Modbusシミュレータを再起動**します(ターミナル1でCtrl+C → もう一度起動)。

   ```
   python simulator/device_simulator.py
   ```
4. 残りのシミュレータとゲートウェイも、ハンズオン3と同じように動かします。別のターミナルで通知Lambdaのログを流しておくと、何が起きているか分かりやすくなります(コマンドは `setup_aws.py` の最後に表示されたものをコピー)。

## ステップ2:異常を起こして通知を受け取る

1. 空調機に異常コード201を発生させます。

   ```
   python simulator/force_alarm.py --code 201
   ```
2. 20〜30秒ほどで「[発生] AHU-01 異常コード 201」というメールが届きます。ゲートウェイが10秒ごとに読み、2回続けて異常だったときに通知するためです。`python aws/show_latest.py` でも alarm_code=201 になっていることを確認します。
3. 異常が出たまま1〜2分待ちます。**2通目は来ません**(状態の変化でだけ通知するため)。ログには通知せずに終わった記録だけが残ります。
4. 解除します。

   ```
   python simulator/force_alarm.py --code 0
   ```

   10〜20秒ほどで「[復旧] AHU-01 異常コード 201」が届きます。本文に発生時刻と復旧時刻(日本時間)が入っています。

## ステップ3:やってみる

| 実験 | 操作 | 期待される結果 |
| --- | --- | --- |
| 瞬時異常 | `python simulator/force_alarm.py --code 202 --pulse 3`(3秒だけ異常にして自動で解除) | メールは来ない。show_latest.py や Athena で alarm_code=202 の行が見えることはあるが、1回だけなのでオンディレイで除外される |
| 通信エラー | Modbusシミュレータ(ターミナル1)をCtrl+Cで止め、30秒待つ | AHU-01 と PLC-LINE1 の「[発生] 通信エラー」が届く。シミュレータを再起動すると「[復旧]」が届く |
| データ途絶 | ゲートウェイをCtrl+Cで止め、3〜4分待つ | 3台分の「[発生] データ途絶」が届く(120秒+チェック間隔1分)。ゲートウェイを再起動すると、1分以内に3台分の「[復旧]」が届く |
| 状態テーブルを見る | 異常を出したまま、DynamoDBコンソールで iot-lab-AlarmStateTable-… の項目を見る | `AHU-01#alarm` の行がある。解除すると消える。「通知済みで未復旧の異常」の一覧そのもの |
| しきい値を変える | template.yaml の `STALE_SEC: '120'` を `'60'` に変えて `setup_aws.py` を再実行し、データ途絶を試す | 通知が早くなる。短すぎると一時的な遅れでも鳴ることを考えて決める値 |

**やってみる(コード変更)**:`aws/lambda/alarm_notifier.py` の on_change の中の `if code and prev:` を `if code:` に変えて `setup_aws.py` を再実行すると、オンディレイが無くなります。しばらくゲートウェイを動かしておくと、シミュレータの一瞬の異常(101や3021)でもメールが来るようになることを確認してから元に戻してください。「通知が鳴りすぎる」状態の体験です。

## 片付け

```
python aws/teardown_aws.py
```

SNSトピック・購読・Lambda・スケジュールもスタックごと削除されます。

**注意**:学習を中断してゲートウェイを止めると、数分後に「データ途絶」のメールが3通届きます。異常ではなく仕様どおりの動きです。スタックを残したままメールを止めたい場合は、届いたメールの末尾の「unsubscribe」リンクで購読を解除します(再開時は `--email` を付けて `setup_aws.py` を再実行すれば登録し直せます)。

## よくあるつまずき

| 症状 | 原因と対処 |
| --- | --- |
| メールが1通も来ない | 確認メールの Confirm subscription を押していない。SNSコンソールのサブスクリプションで状態が「確認済み」か確認する。迷惑メールフォルダも見る |
| force_alarm.py が「接続できません」 | Modbusシミュレータが動いていない |
| force_alarm.py は成功するのに alarm_code が変わらない | シミュレータが古いまま。ステップ1の3の通り、再起動して新しい device_simulator.py を読み込む |
| 「[発生]」は来たが「[復旧]」が来ない | ゲートウェイが止まっている(復旧も最新値の変化で判定するため)。ゲートウェイを動かす |
| ゲートウェイを止めていないのに「データ途絶」が来る | PCの時計がずれている。Windowsの「設定 → 時刻と言語 → 今すぐ同期」 |
| 通知Lambdaのログに `AccessDeniedException` | template.yaml の AlarmNotifierRole を書き換えた場合は、対象のテーブル・トピックと操作が合っているか確認 |
