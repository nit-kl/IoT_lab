# 作業手順（AWS での動作確認）

`factory-replay` を自分の AWS 環境で動かして確認するための手順。ステップが進むたびに追記する。
方針は [実現方針.md](実現方針.md)、各スクリプトの詳細は [factory-replay/README.md](../factory-replay/README.md) を参照。

以下のコマンドは PowerShell で、`factory-replay` フォルダで実行する前提。
`<owner>` は自分の名前（英小文字で始まる英小文字・数字 2〜16 文字。例: `kojima`）に置き換える。

## 0. 事前準備（初回のみ）

| 必要なもの | 確認コマンド |
|---|---|
| Python 3.10 以上 | `python --version` |
| AWS CLI v2 | `aws --version` |

PC 全体の Python を汚さないよう、`factory-replay` 専用の仮想環境（venv）を作ってその中にライブラリを入れる。

```powershell
cd factory-replay
python -m venv .venv                 # 仮想環境を作る（初回のみ）
.\.venv\Scripts\Activate.ps1         # 有効化。プロンプトの先頭に (.venv) と出れば OK
pip install -r requirements.txt
```

- 以降の手順は、**毎回ターミナルを開いたら `.\.venv\Scripts\Activate.ps1` で有効化してから** 実行する
- `このシステムではスクリプトの実行が無効になっているため…` と出たら、次を一度だけ実行してから有効化し直す

  ```powershell
  Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
  ```

- 終わるときは `deactivate`。`.venv` フォルダは Git 管理外

## 1. AWS にログインする

```powershell
aws login
aws sts get-caller-identity          # 自分のアカウント・ユーザーが表示されれば OK
aws configure get region             # ap-northeast-1 であること
```

- `Your session has expired` と出たら、もう一度 `aws login` する
- リージョンが違う場合は、各スクリプトに `--region ap-northeast-1` を付ける（既定は ap-northeast-1）

## 2. ステップ 1：サンプル CSV を確認する（AWS 不要）

```powershell
python tools/generate_csv.py --out "$env:TEMP\check.csv"
```

- `21,600 行 / 1.3 MB` と表示されること
- 同梱の `data/factory_sample.csv` と同じ内容になること（`fc.exe data\factory_sample.csv "$env:TEMP\check.csv"` で差分なし）

## 3. ステップ 2：AWS 環境を作成する

```powershell
python aws/setup_aws.py --owner <owner>
```

- 初回は Aurora の作成に **10〜15 分** かかる
- 最後に次のように表示されれば成功

  ```
  スタックの作成が完了しました
  DB に接続しています（一時停止中なら再開まで数十秒かかります）...
  テーブルを作成しました: staging_readings, readings, replay_state

  スタック名 : xcp-factory-<owner>
  バケット   : xcp-factory-<owner>-data-<アカウントID>
  クラスター : arn:aws:rds:ap-northeast-1:<アカウントID>:cluster:xcp-factory-<owner>
  ```

- もう一度実行すると「スタックに変更はありません」と出て、テーブル作成だけやり直す（中身は消えない）

### 確認 1：コンソールで作成物を見る

| 画面 | 確認すること |
|---|---|
| CloudFormation > スタック | `xcp-factory-<owner>` が `CREATE_COMPLETE` |
| RDS > データベース | クラスター `xcp-factory-<owner>` があり、インスタンスが `db.serverless` |
| RDS > クラスター > 設定 | 容量が 0〜4 ACU、自動一時停止が有効、RDS Data API が有効 |
| S3 | バケット `xcp-factory-<owner>-data-<アカウントID>` がある |
| タグ | 各リソースに `Project=xcp-factory`, `Owner=<owner>` が付いている |

### 確認 2：テーブルができていることを SQL で見る

スタックの出力を変数に入れてから、Data API で SQL を実行する。

```powershell
$stack = "xcp-factory-<owner>"
$cluster = aws cloudformation describe-stacks --stack-name $stack --query "Stacks[0].Outputs[?OutputKey=='ClusterArn'].OutputValue" --output text
$secret  = aws cloudformation describe-stacks --stack-name $stack --query "Stacks[0].Outputs[?OutputKey=='SecretArn'].OutputValue" --output text

function sql($q) {
  aws rds-data execute-statement --resource-arn $cluster --secret-arn $secret --database factory `
    --format-records-as JSON --query formattedRecords --output text --sql $q
}

sql "SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' ORDER BY 1"
sql "SELECT extname FROM pg_extension ORDER BY 1"
sql "SELECT * FROM replay_state"
```

| SQL | 期待する結果 |
|---|---|
| テーブル一覧 | `readings`, `replay_state`, `staging_readings` |
| 拡張一覧 | `aws_commons`, `aws_s3`, `plpgsql` を含む |
| `replay_state` | 1 行だけで、`status` が `idle`、`speed` が `60` |

- `DatabaseResumingException` が出たら DB が一時停止から再開中。数十秒待って再実行する

#### コンソール（RDS クエリエディタ）で見る場合

コマンドを使わず、ブラウザから同じ SQL を実行できる（Data API を有効にしているので使える）。

1. AWS コンソールで **RDS** を開き、左メニューの **クエリエディタ** を選ぶ
2. 接続画面で次のように入力して **データベースに接続します** を押す

   | 項目 | 入力値 |
   |---|---|
   | データベースインスタンスまたはクラスター | `xcp-factory-<owner>` |
   | データベースユーザー名 | **Secrets Manager ARN と接続する** を選ぶ |
   | Secrets Manager ARN | スタックの出力 `SecretArn`（CloudFormation > `xcp-factory-<owner>` > 出力 タブからコピー。`arn:aws:secretsmanager:…:secret:rds!cluster-…`） |
   | データベース名 | `factory` |

3. エディタに SQL を書いて **実行** を押す。例:

   ```sql
   SELECT * FROM replay_state;
   SELECT count(*) FROM readings;
   SELECT equipment_id, metric, value, ts, source_ts FROM readings ORDER BY seq DESC LIMIT 20;
   ```

- DB が一時停止中だと最初の実行がエラーになる。数十秒待って再実行する
- 時刻は UTC で表示される（日本時間で見たいときは `ts AT TIME ZONE 'Asia/Tokyo'` のように書く）
- 一度に表示されるのは結果の先頭部分のみ。大量の行は `LIMIT` を付けて見る
- エラーで接続できない場合は、自分の IAM 権限に RDS Data API とシークレット読み取り（`rds-data:*`、`secretsmanager:GetSecretValue`）があるか確認する
- 開きっぱなしでも、SQL を実行しなければ 5 分で DB は一時停止する

### 確認 3：使っていない間に一時停止すること

最後の SQL から **5 分以上** 何もしないで待ち、CloudWatch > メトリクス > RDS で
クラスター `xcp-factory-<owner>` の `ServerlessDatabaseCapacity` が **0** になっていることを確認する。
0 の間は ACU の課金がかからない（ストレージ代のみ）。

## 4. ステップ 3：CSV をアップロードして少しずつ反映させる

### 4-1. 環境を更新する

ステップ 3 の Lambda（loader / replayer）と 1 分ごとのスケジュールを追加する。同じコマンドを再実行するだけでよい。

```powershell
python aws/setup_aws.py --owner <owner>
```

- 初回だけ `Lambda コード用バケット xcp-factory-<owner>-artifacts-<アカウントID> を作成しました` と出る
- `スタックの更新が完了しました` → `テーブルと関数を作成しました: … start_replay()` と出れば成功（数分）
- 最後に表示される `aws s3 cp …` のコマンドが、次で使うアップロードコマンド

### 4-2. CSV をアップロードする

```powershell
$stack  = "xcp-factory-<owner>"
$bucket = aws cloudformation describe-stacks --stack-name $stack --query "Stacks[0].Outputs[?OutputKey=='BucketName'].OutputValue" --output text
aws s3 cp data/factory_sample.csv "s3://$bucket/incoming/"
```

`incoming/` の下に `.csv` を置くと自動で取り込みが始まる（それ以外の場所・拡張子は無視される）。

### 確認 4：取り込まれてリプレイが始まること

確認 2 で定義した `$cluster` `$secret` と `sql` 関数を使う（新しいターミナルなら確認 2 の定義部分をもう一度実行する）。

```powershell
sql "SELECT status, total_rows, cursor_seq, speed, source_key, message FROM replay_state"
aws scheduler get-schedule --name "$stack-replayer" --query State --output text
```

| 項目 | 期待する結果（アップロードから 1 分以内） |
|---|---|
| `status` | `running`（取り込み中は `loading`。`error` なら `message` に理由） |
| `total_rows` | `21600` |
| `speed` | `60` |
| `source_key` | `incoming/factory_sample.csv` |
| スケジュールの状態 | `ENABLED` |

### 確認 5：1 分ごとに少しずつ増えること

数分おきに次を実行する。

```powershell
sql "SELECT count(*) AS rows, max(source_ts) AS csv_time FROM readings"
sql "SELECT round(cursor_seq * 100.0 / total_rows, 1) AS percent FROM replay_state"
```

- 60 倍速なので、**1 分ごとに約 900 行**（CSV の 1 時間分）ずつ増える
- `csv_time`（CSV 上の時刻）が 1 分ごとに約 1 時間ずつ進む
- 中身を見る:

  ```powershell
  sql "SELECT equipment_id, metric, value, ts, source_ts FROM readings ORDER BY seq DESC LIMIT 5"
  ```

  `ts` は反映時刻に読み替えた時刻、`source_ts` は CSV 上の元の時刻。Data API の表示は UTC（日本時間 −9 時間）

- Lambda のログ:

  ```powershell
  aws logs tail "/aws/lambda/$stack-loader" --since 30m
  aws logs tail "/aws/lambda/$stack-replayer" --follow       # Ctrl+C で終了
  ```

  replayer は毎分 `{"msg": "反映", "moved": 900, ...}` のようなログを出す

### 確認 6：最後まで流れたら止まること

1 日分は約 **24 分** で流れ終わる。終わったら次を確認する。

| 確認 | 期待する結果 |
|---|---|
| `sql "SELECT status, cursor_seq, total_rows FROM replay_state"` | `done`、`cursor_seq = total_rows = 21600` |
| `sql "SELECT count(*) FROM readings"` | `21600` |
| `aws scheduler get-schedule --name "$stack-replayer" --query State --output text` | `DISABLED` |
| replayer のログ | `リプレイ完了。スケジュールを停止` |
| その 5 分以上後の CloudWatch `ServerlessDatabaseCapacity` | `0`（一時停止） |

### 確認 7（任意）：壊れた CSV を置いたとき

```powershell
"this,is,not,valid" | Out-File -Encoding utf8 "$env:TEMP\bad.csv"
aws s3 cp "$env:TEMP\bad.csv" "s3://$bucket/incoming/bad.csv"
sql "SELECT status, message FROM replay_state"      # 1 分以内に status = error、message に理由
sql "SELECT count(*) FROM readings"                  # 直前のデータは消えずに残っている
```

元に戻すには、正しい CSV をもう一度アップロードする（`aws s3 cp data/factory_sample.csv "s3://$bucket/incoming/"`）。

### 確認 8（任意）：大きい CSV

```powershell
python tools/generate_csv.py --days 30 --interval 10s --out data/month.large.csv    # 約 390 万行 / 230 MB
aws s3 cp data/month.large.csv "s3://$bucket/incoming/"
sql "SELECT status, total_rows, updated_at FROM replay_state"
```

- しばらく `loading` が続き（数分程度）、その後 `running`・`total_rows = 3888000` になること
- 取り込み中も `sql "SELECT count(*) FROM readings"` は直前のデータを返すこと（取り込み完了時に空になって再スタート）
- 60 倍速だと 30 日分は約 12 時間かかる。確認できたら `data/factory_sample.csv` をアップロードし直して小さいデータに戻すか、後片付けする
  （再生速度の変更はステップ 5 のリセット機能で行う）

## 5. 後片付け

検証を終えるとき、またはやり直したいときに実行する。DB の中身と S3 の CSV はすべて消える。

```powershell
python aws/teardown_aws.py --owner <owner>     # yes と入力すると削除開始（10 分ほど）
```

- 「削除が完了しました」と出たら、CloudFormation にスタックが残っていないこと、RDS・S3（データ用・Lambda コード用の 2 つ）・Lambda・EventBridge Scheduler に `xcp-factory-<owner>` が残っていないことを確認する

## うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| `Your session has expired` / `Unable to locate credentials` | `aws login` をやり直す |
| `MissingDependencyException: ... pip install "botocore[crt]"` | `aws login` の認証情報を使うための追加ライブラリが入っていない。`pip install -r requirements.txt` をやり直す（`boto3[crt]` が入る） |
| `ModuleNotFoundError: No module named 'boto3'` | 仮想環境が有効になっていない。`.\.venv\Scripts\Activate.ps1` を実行する（初回なら「0. 事前準備」から） |
| `--owner は英小文字で始まる…` | 名前のルール違反。英小文字で始め、英小文字・数字のみ 2〜16 文字にする |
| `スタックの作成に失敗しました` | `aws cloudformation describe-events --stack-name xcp-factory-<owner>` で失敗したリソースと理由を確認。ロールバック完了後に `teardown_aws.py` で消してから再実行する |
| 失敗理由が `The maximum number of VPCs has been reached` | リージョンの VPC 上限（既定 5）。不要な VPC を消すか、Service Quotas で上限緩和を申請する |
| 失敗理由に `already exists` | 同名のリソースが残っている。`teardown_aws.py` を実行してから再作成する |
| 失敗理由に `MinCapacity` / `SecondsUntilAutoPause` の非対応 | 既定のエンジンバージョンが 0 ACU 非対応の可能性。報告してほしい（テンプレートでバージョンを指定する） |
| `DatabaseResumingException` が続く | 一時停止からの再開待ち。1 分ほど待って再実行する |
| アップロードしても `replay_state` が変わらない | 置き場所が `incoming/` 直下で拡張子が `.csv` か確認。`aws logs tail "/aws/lambda/$stack-loader" --since 30m` で loader が動いたか見る |
| `status` が `error`、`message` が `unable to access credentials stored with the database instance` | DB の再開直後やスタック更新直後に、DB が S3 取り込み用ロールの認証情報をまだ取得できていない（数分で解消する一時的な状態）。loader は自動で 2 分ほど再試行するが、それでも失敗したら数分待って CSV をもう一度アップロードする |
| `status` が `error`（上記以外） | `message` に理由が入っている。CSV の列（`ts,line_id,equipment_id,metric,value,unit` のヘッダー付き）を確認して正しい CSV を置き直す |
| `status` が `running` なのに件数が増えない | スケジュールが `DISABLED` になっていないか確認（スタック更新で DISABLED に戻ることがある）。CSV をもう一度アップロードすると再開する |
| `loading` のまま 30 分以上変わらない | replayer・loader のログを確認。CSV を置き直すとやり直せる |
