# IoT学習ハンズオン5:遠隔操作

Oct 12, 2026 · @Reo Kojima

前提:[IoT学習ハンズオン3](./IoT学習ハンズオン3%20Lambda+DynamoDB最新値.md)まで終わっていて、`python aws/show_latest.py` で最新値が見えることです。[ハンズオン4](./IoT学習ハンズオン4%20アラーム通知.md)は必須ではありません。所要時間は60〜90分です。費用は数時間の学習なら1円未満です(命令を送った回数ぶんだけ課金)。

## 全体像

これまでのキットは「機器 → クラウド」の一方通行でした。今回は逆向きに、**クラウドから空調機の設定温度を変えます**。

```
send_command.py ──① 命令テーブルに「sent」で記録
      │
      └──② lab/gw01/AHU-01/cmd ──→ AWS IoT Core ──→ ゲートウェイ ──③ 安全確認 → Modbusで書き込み → 読み返し
                                                          │
命令テーブル ←── ⑤ IoTルール(DynamoDBv2)←── ④ lab/gw01/AHU-01/cmd_result
```

| 追加・変更するもの | 役割 | 学べること |
| --- | --- | --- |
| gateway/points.json の `writable` | 書き込んでよいポイントと値の範囲 | 書き込みは「許可したものだけ」にする |
| gateway/gateway.py の遠隔操作部分 | 命令を受け取り、安全確認して書き込み、結果を返す | 期限・冪等性・範囲チェック・読み返し |
| aws/template.yaml の GatewayPolicy | gw01 が自分宛ての命令だけ購読・受信できる権限 | 送信だけでなく受信も最小権限にする |
| aws/template.yaml の CommandTable / CommandResultRule | 命令と結果を1件1行で残す | 監査ログ(誰が・いつ・何を・どうなったか) |
| aws/send_command.py | 命令を送って結果を待つ | 命令IDで送信と結果を結びつける |
| simulator/device_simulator.py | 設定温度(レジスタ2番)を外から書き換えられるようにした | 書いた設定温度に向かって室温が動く |

**読むより書く方が危ない**:読み取りの不具合は「グラフがおかしい」で済みますが、書き込みの不具合は機器を止めたり、壊したり、人に危険が及んだりします。このハンズオンでは、そのための確認を何重にも入れています。**実機では、設備の管理者の許可なく書き込みを試さないでください。**

## 命令の安全確認

ゲートウェイは命令を受け取ると、次の順に確認します。1つでも引っかかったら機器には何もせず、理由を付けて「rejected(拒否)」を返します。

| 順番 | 確認 | 理由 |
| --- | --- | --- |
| 1 | 同じ command_id を実行済みなら、実行せず前回の結果を返す | QoS1 は同じ命令が2回届くことがある。「設定温度を1℃下げる」のような命令が2回実行されると事故になる(冪等性) |
| 2 | 期限(expires_at)を過ぎていたら実行しない | 回線の遅れで数分後に届いた命令は、もう誰も望んでいないかもしれない |
| 3 | points.json で `writable` が書かれたポイントだけ書く | 室温や異常コードなど、読み取り専用のものを書き換えさせない |
| 4 | 値が `writable` の min〜max の範囲内か | 打ち間違い(24.5 のつもりの 245)で機器に無理をさせない |
| 5 | 書く前の値を読み、書いて、読み返して一致を確認 | 「書いたつもり」で終わらせない。違えば failed(失敗)を返す |

実装上の工夫もいくつかあります。

- **命令はメインループで実行**:MQTTの受信は別スレッドで起きます。そこで直接Modbusを触ると、定期の読み取りと通信がぶつかります。受信したらキューに積むだけにして、読み取り周期の合間にメインループで1件ずつ実行します。
- **購読は接続のたびにやり直す**:MQTTは再接続すると購読が消えることがあります。`on_connect` の中で購読しているので、回線断から復旧しても命令が届きます。接続時に1回だけ購読する作りにして「回線が一度切れたら命令が届かなくなった」というのは、よくある不具合です。
- **結果もバッファ経由で返す**:テレメトリと同じSQLiteバッファに積むので、返す瞬間に回線が切れても結果は失われません。
- **宛先はトピックで決める**:メッセージ本文に別の機器IDが書いてあっても、トピック `lab/gw01/AHU-01/cmd` の AHU-01 を使います。IoTポリシーで受信を絞っているのはトピックなので、宛先をトピックに一本化しておくと権限とずれません。

**ハンズオン3との対比**:命令テーブルへの書き込みには、Lambdaを使わずIoTルールのDynamoDBv2アクションを使っています。ハンズオン3では「順番が入れ替わると最新値が巻き戻る」ためにLambdaの条件付き書き込みが必要でした。命令は command_id ごとに1行で、上書きされても困らない(結果で上書きされるのが正しい)ので、直接書くだけで十分です。同じDynamoDBへの書き込みでも、データの性質で選び方が変わります。

## ステップ1:AWS環境とシミュレータを更新する

1. `setup_aws.py` を再実行します。IoTポリシーに購読・受信の権限が追加され、命令テーブルとルールが作られます(1〜3分)。証明書は再利用されます。

   ```
   python aws/setup_aws.py
   ```
2. **Modbusシミュレータを再起動**します(ハンズオン4で再起動済みなら不要)。新しいシミュレータは設定温度をレジスタから読むので、書き込んだ値が反映されます。
3. **ゲートウェイを再起動**します。新しい gateway.py は起動時に命令トピックを購読します。

   ```
   python gateway/gateway.py
   ```
4. 別のターミナルで最新値を流しておきます。

   ```
   python aws/show_latest.py --watch 5
   ```

## ステップ2:設定温度を変える

1. AHU-01 の設定温度を 24.5℃ にします。

   ```
   python aws/send_command.py --value 24.5
   ```

   数秒で次のように表示されます。

   ```
   送信: lab/gw01/AHU-01/cmd  setpoint_c=24.5  command_id=3f0c…  期限=60秒
   結果: done
         変更前 26.0 → 変更後 24.5
   ```
2. ゲートウェイのログには `命令 3f0c… AHU-01 setpoint_c=24.5 → done` が出ます。
3. show_latest.py で setpoint_c が 24.5 になり、room_temp_c が数分かけて24.5℃に近づいていくことを確認します(空調機が運転中のとき。シミュレータは10分のうち2分停止します)。ハンズオン2のGrafanaを動かしていれば、室温のグラフでも下がっていく様子が見えます。
4. 元に戻します。

   ```
   python aws/send_command.py --value 26.0
   ```

## ステップ3:やってみる

| 実験 | 操作 | 期待される結果 |
| --- | --- | --- |
| 範囲外 | `python aws/send_command.py --value 35` | `rejected(理由: 範囲外の値: 35.0(許可 18.0〜30.0))`。機器には何も書かれない |
| 期限切れ | `python aws/send_command.py --value 24.0 --ttl -10` | `rejected(理由: 期限切れ)` |
| 読み取り専用 | `python aws/send_command.py --point room_temp_c --value 20` | `rejected(理由: 書き込み禁止のポイント: room_temp_c)` |
| 重複 | `python aws/send_command.py --value 25.0 --command-id test-1` を2回 | 2回目は「再実行せず前回の結果を返しました」と表示。ゲートウェイのログにも「重複のため再実行せず」 |
| ゲートウェイ停止中 | ゲートウェイをCtrl+Cで止めてから `python aws/send_command.py --value 24.0` | 30秒待っても結果が返らない。その後ゲートウェイを起動しても、この命令は**実行されない**(下の解説) |
| 機器の通信エラー | Modbusシミュレータを止めてから `python aws/send_command.py --value 24.0` | `failed`。通信できなければ書けない |
| 監査ログ | DynamoDBコンソールで iot-lab-CommandTable-… の項目を見る | 送った命令がすべて残っている。issued_by(誰が)、issued_at(いつ)、value(何を)、status・before・after(どうなったか) |

**ゲートウェイ停止中の命令が届かない理由**:このゲートウェイは「クリーンセッション」でMQTTに接続しているので、つながっていない間の命令はIoT Coreに保持されません。届かないのは不便に見えますが、遠隔操作では安全側の動きです。もし保持して後から届けると、1時間前に送った命令が突然実行されることになります。後から届けたい場合でも、ステップ1の「期限」の確認が必須になります。

「つながったら最新の設定を反映してほしい」という用途には、AWS IoT の **Device Shadow**(機器の「あるべき状態」と「今の状態」をクラウド側に持つ仕組み)が向いています。命令(1回きりの操作)と、あるべき状態(いつでも同じになってほしい値)の違いを意識しておくと、設計で迷いにくくなります。

## 片付け

```
python aws/teardown_aws.py
```

命令テーブルもスタックごと削除されます。ゲートウェイ側の実行済み命令の記録は `gateway/buffer.db` の commands テーブルに残ります(ファイルごと消して構いません)。

## よくあるつまずき

| 症状 | 原因と対処 |
| --- | --- |
| send_command.py が「結果が返りませんでした」 | ゲートウェイが動いていない、`--console` で動いている(MQTT接続していない)、または古い gateway.py のまま。ゲートウェイを再起動する |
| ゲートウェイは動いているのに命令が届かない(ログに「命令」が出ない) | `setup_aws.py` を再実行していないため、ポリシーに購読・受信の権限が無い。再実行してからゲートウェイを再起動 |
| 結果は done なのに show_latest.py の設定温度が変わらない | 次の読み取り周期(最大10秒)と最新値の反映を待つ。それでも変わらなければ、Modbusシミュレータが古いまま(再起動する) |
| 結果が failed「読み返した値が違う」 | シミュレータが古いまま(設定温度を毎秒26.0℃で上書きしている)。再起動する |
| 期限切れでないはずなのに「期限切れ」で拒否される | PCの時計がずれている。期限はゲートウェイの時計で判断するため。Windowsの「設定 → 時刻と言語 → 今すぐ同期」 |
| `AccessDeniedException`(iot-data の Publish) | 自分のAWSユーザーに IoT への Publish 権限が無い。管理者権限のユーザーで実行するか、`iot:Publish` を付与 |
