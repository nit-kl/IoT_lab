MQTT（エムキューティーティー）は、**IoT機器がインターネット越しにデータを送るための、軽くてシンプルな通信のルール**です。1999年に石油パイプラインの監視（衛星回線のような細くて不安定な回線）のために作られたのが始まりで、今はAWS IoT Coreをはじめ、IoTクラウドの事実上の標準になっています。

## 一言でいうと「掲示板（ブローカー）を介した伝言」

Modbusは「聞く側が機器に直接問い合わせる」仕組みでした。MQTTは違って、**送る側と受け取る側が直接つながらず、間に立つ「ブローカー」を介してやり取りします。**

- **パブリッシュ（送信）**:送る側は「宛先の人」ではなく、**トピック**という住所のような文字列を付けてブローカーに送ります。誰が受け取るのかは知りません。
- **サブスクライブ（購読）**:受け取る側は、事前にブローカーへ「このトピックのメッセージがほしい」と登録しておきます。
- **ワイルドカード**:`+` は1階層分、`#` はそれ以下すべてにマッチします。`lab/+/+/telemetry` なら全ゲートウェイの全機器分が届きます。

送る側と受け取る側が互いを知らなくていいので、受け取る側（分析、アラート、ダッシュボードなど）を後からいくらでも増やせます。機器側のプログラムは変えずに済みます。

## IoTで使われる理由

- **軽い**:ヘッダーが最小2バイトと小さく、細い回線や電池で動く機器でも負担が少ないです。
- **つなぎっぱなし**:一度接続したら維持し続けるので、毎回接続し直すHTTPより効率がいいです。
- **機器側から外へつなぐ**:ゲートウェイからクラウドに向けて接続するので、工場やビルのファイアウォールに「外から入ってくる穴」を開けずに済みます。セキュリティ上、とても大きな利点です。
- **途切れる前提の仕組みがある**:再接続、届いたかの確認（QoS）、切断を知らせる機能などが最初から用意されています。

## 押さえておきたい用語

| 用語 | 意味 | キットでの使われ方 |
|---|---|---|
| QoS 0 | 送りっぱなし。届かなくても再送しない | 使っていない |
| QoS 1 | 届くまで再送する。ただし重複して届くことがある | 使っている。受領通知（PUBACK）が返ったものだけバッファから消す |
| QoS 2 | ちょうど1回だけ届ける。やり取りが増えて重い | AWS IoT Coreは非対応 |
| Retain | トピックの最新メッセージを1件ブローカーに残し、後から購読した人にも渡す | 使っていない（「機器の最新状態」に便利） |
| LWT（遺言） | 機器が突然切断されたときに、ブローカーが代わりに送るメッセージ | 使っていない（死活監視に便利） |
| Keep alive | 通信がないときも定期的に生存確認をする間隔 | 60秒 |

キットでQoS 1を選び、メッセージに `message_id` を付けているのはこのためです。「取りこぼさないこと」を優先すると重複はどうしても起こり得るので、重複はDB側で取り除く、というのが実務の定石です。

## Modbus・MCプロトコルとの役割分担

| | Modbus / MCプロトコル | MQTT |
|---|---|---|
| 使う場所 | 工場やビルの中（機器とゲートウェイの間） | インターネット越し（ゲートウェイとクラウドの間） |
| やり取りの形 | 聞く側が問い合わせ、機器が答える | 送る側がトピックに送り、ブローカーが配る |
| 中身 | 番号付きの棚の数字だけ | 自由（キットでは意味の分かるJSON） |
| セキュリティ | 基本的にない | TLS暗号化と証明書による認証 |

つまり、ゲートウェイの役目は**「現場の言葉（Modbus、MCプロトコル）で聞いた数字を、クラウドの言葉（MQTT＋JSON）に翻訳して送ること」**です。

実際の動きは、手順書のステップ3で、AWSコンソールの「MQTTテストクライアント」から `lab/#` を購読すると目で確かめられます。ゲートウェイが10秒ごとに送るメッセージが、届いた順に表示されます。
