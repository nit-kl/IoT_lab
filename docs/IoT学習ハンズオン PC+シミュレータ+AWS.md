# IoT学習ハンズオン:PC+シミュレータ+AWS

Oct 15, 2026 · @Reo Kojima

## 全体像

題材はスーパー1店舗です。PC1台の上で店舗の設備(売場空調・冷蔵ショーケース・電力計・バックヤードの冷凍機盤)を模擬し、自作の店舗ゲートウェイでModbusとMCプロトコルで読み取ってMQTTで送り、AWS IoT Core経由でS3に貯めてAthenaのSQLで分析するところまでを通します。所要時間は準備込みで半日〜1日です。費用はAWS新規アカウントの無料プランならクレジット内に収まり、既存アカウントでも学習で数時間動かすだけなら数円〜十数円です(時間課金のサービスは作りません)。

&#91;embedded content: 学習キットの構成 · PC側2つ、AWS側4つ\]

PC側は自分で書いたコードが動く範囲、AWS側はCloudFormationで一括作成・一括削除できる範囲です。

模擬する設備は次の4台です。スーパーの設備データとしてよく扱うものを選んでいます。

| 機器ID | 設備 | 通信 | 主な値 | このキットでの役割 |
| --- | --- | --- | --- | --- |
| AC-01 | 売場空調 | Modbus TCP(ポート5021) | 室温、設定温度、運転状態、異常コード | 遠隔操作(ハンズオン5)の対象 |
| RC-01 | 冷蔵ショーケース(飲料・日配) | Modbus TCP(ポート5022) | 庫内温度、霜取り中、扉開、異常コード | 食品の温度管理(HACCP)。アラーム通知(ハンズオン4)の主役 |
| PM-01 | 電力計(店舗の受電) | Modbus TCP(ポート5023) | 積算電力量、瞬時電力 | ワード順の読み解き。電力のデマンド管理 |
| REF-01 | 冷凍機盤(バックヤード) | MCプロトコル(三菱電機 iQ-R、ポート5010) | 冷凍庫温度、圧縮機の運転・発停回数、圧力、異常コード | PLCのデバイス表の読み解き |

シミュレータは**1機器=1プロセス**で、機器ごとに別のポートで待ち受けます。実際の店舗でも空調のコントローラ・ショーケース・電力計・冷凍機盤は別々の機器で、それぞれ自分のIPアドレスを持ち、1台だけ電源が落ちる・LANケーブルが抜ける、ということが普通に起きます。その「1台だけの故障」を再現できるようにするためです(ポートの違いが、実機のIPアドレスの違いに当たります)。ゲートウェイは、ポイントリストに機器ごとに書いた接続先(host・port)に接続します。

このキットはXCPチームの検証用です。チームで同じAWSアカウントを使うので、AWSに作るものの名前にはすべて自分の名前(owner)を入れて区別します(命名のきまりは後述)。

使うのは学習キット iot-lab.zip です。中身は次のとおりです。

| ファイル | 役割 | 学べること |
| --- | --- | --- |
| simulator/aircon.py・showcase.py・power\_meter.py | 売場空調・冷蔵ショーケース・電力計を1台ずつ模擬するModbus TCPサーバー | レジスタ、スケーリング、ワード順 |
| simulator/refrigerator\_plc.py | 冷凍機盤のPLC(iQ-R)を模擬するMCプロトコルサーバー | PLCのデバイス(D・M) |
| simulator/run\_store.py | 上の4つ(とハンズオン6の入店カウンタ・POS)をまとめて起動し、ログを1画面に出す | 1機器=1サービスの構成 |
| gateway/points.json | ポイントリスト(タグ表) | 現場で最初に入手すべき資料の形 |
| gateway/gateway.py | 収集→変換→バッファ→MQTT送信 | ストア&フォワード、UTC、連番、QoS1 |
| aws/template.yaml | IoTポリシー、ルール、S3、Glueテーブル、Athena | 最小権限、ルールエンジン、パーティション |
| aws/setup\_aws.py / teardown\_aws.py | AWS環境の作成・削除、証明書発行 | X.509証明書による機器認証、後片付け |
| aws/naming.py | リソースの命名のきまり | 共用アカウントでの命名とタグ |
| aws/queries.sql | Athenaのサンプルクエリ | 時系列集計、HACCPの温度記録、電力のデマンド、遅延・欠損・重複の確認 |

## 準備(30〜60分)

Python、AWSアカウント、AWS CLIの3つと、予算アラートを用意します。Windows・Mac・Linuxどれでも同じ手順で動きます。以下のコマンドはWindowsのPowerShell向けです(ターミナルを複数使うときはPowerShellの窓を複数開きます)。

1. **Python 3.10以上**をpython.orgのインストーラで入れます。最初の画面で「Add python.exe to PATH」にチェックを入れてください。PowerShellで `python --version` と打ってバージョンが出ればOKです(Microsoft Storeが開く場合はPATH設定漏れなので、インストーラをやり直します)。
2. iot-lab.zipを右クリック→「すべて展開」し、そのフォルダでPowerShellを開いて(フォルダの空白部分をShift+右クリック→「PowerShellウィンドウをここで開く」、またはエクスプローラーのアドレス欄に `powershell` と入力)、仮想環境を作ります。

   ```
   python -m venv .venv
   .venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```

   `Activate.ps1` で「スクリプトの実行が無効」というエラーが出たら、先に次の1行を実行してから再度有効化します。

   ```
   Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
   ```

   行頭に (.venv) と表示されていれば有効です。新しいPowerShellの窓を開いたときは、毎回 `.venv\Scripts\Activate.ps1` を実行してください。
3. **AWSアカウント**を用意します。チームの検証用アカウントを使う場合は、管理者から IAM Identity Center のユーザーをもらいます。自分でアカウントを作る場合は、ルートユーザーにMFAを設定し、普段の作業は IAM Identity Center かIAMユーザーで行います。
4. **AWS CLI v2**をWindows用インストーラ(.msi)で入れ、PowerShellを開き直してから `aws configure sso`(IAM Identity Center)または `aws configure`(アクセスキー)で認証を設定します。`aws sts get-caller-identity` でアカウントIDが表示されればOKです。
5. **予算アラート**:Billing and Cost Management の Budgets で月額 5 USD 程度の予算を作り、メール通知を設定します。課金の事故を防ぐ一番効く対策です(チームの共用アカウントなら、管理者が設定済みか確認します)。
6. **owner を決める**:AWSに作るものの名前に入れる、自分を表す名前です。英小文字と数字だけ、16文字以内にします(例:`kojima`)。チームの中で他の人と重ならないようにしてください。
7. 初回にシミュレータを起動したとき「Windowsセキュリティの重要な警告」(ファイアウォール)が出たら、「プライベートネットワーク」だけ許可します。このキットはPC内(127.0.0.1)で通信するので、許可しなくても動作します。

リージョンは東京(ap-northeast-1)を前提にしています。変える場合は setup/teardown に `--region` を付けます。

## ステップ1:店舗の設備を読む(Modbus・MCプロトコル)

ゴールは、生のレジスタ値(16bitの数字の並び)を「庫内温度5.1℃」のような意味のある値に直せるようになることです。AWSはまだ使いません。

1. ターミナル1で、店舗の設備シミュレータをまとめて起動します。4台が別々のプロセスとして起動し、1秒ごとに値が変化します。

   ```
   python simulator/run_store.py --verbose
   ```

   `[AC-01 ] AC-01 売場空調 起動: 127.0.0.1:5021` のように、機器ごとに1行ずつ表示されます。各機器は `python simulator/showcase.py` のように1台ずつ起動することもできます(ステップ2で使います)。
2. ターミナル2で、ゲートウェイを「画面表示のみ・生値表示あり」で1回動かします。

   ```
   python gateway/gateway.py --console --dump-raw --once
   ```
3. 次のような出力を見比べます(実際に動かした結果の抜粋)。

   ```
   [raw] RC-01      2      0x0033         -> case_temp_c=5.1
   [raw] PM-01      0      0xD687 0x0012  -> energy_kwh=123456.7
   [raw] PM-01      2      0x423B 0xA5A5  -> power_kw=46.912
   [raw] REF-01     D104   0xA868 0xC1A2  -> freezer_temp_c=-20.332
   ```

読み解きのポイントは3つです。

- **スケーリング**:0x0033 = 51。ポイントリストの scale 0.1 を掛けて5.1℃。小数を整数×10で持つのは空調・ショーケース・PLCで非常によくある形です。冷凍庫のようにマイナスになる値は「符号付き16bit(s16)」として読みます。
- **ワード順**:電力計の積算電力量は 0xD687, 0x0012 の順。下位ワードが先なので値は 0x0012D687 = 1,234,567、scale 0.1 を掛けて123,456.7kWh。逆に読むと 0xD6870012 となり、3億5,991万kWhという大きな値になります。
- **浮動小数点**:瞬時電力は2ワードでIEEE754の32bit浮動小数点。0x423BA5A5 ≒ 46.9kW。ワード順を逆にすると全く違う数字になります。冷凍機盤の冷凍庫温度も同じ形式ですが、こちらは下位ワードが先です(同じ店舗の中でも、機器ごとにワード順が違うのは普通のことです)。

**やってみる**:gateway/points.json の PM-01 の energy\_kwh の type を `u32_hw` に変えて再実行し、値が化けることを確認してから元に戻してください。実機で「値がおかしい」ときの最初の疑いどころです。

**冷凍機盤のデバイス表**:REF-01 は、PLCのプログラマから受け取る「デバイス表」(D100は発停回数、M0は圧縮機運転中、…)を、そのままポイントリストに書き写した形です。`--verbose` を付けたので、ターミナル1の `[REF-01]` の行に、ゲートウェイがどのデバイスを読んだかが表示されます。

## ステップ2:ゲートウェイの中身を理解する

gateway.py は「読む→変換→1台1メッセージのJSONにする→バッファに積む→送れたら消す」を10秒ごとに繰り返します。送られるメッセージは次の形です。

```
topic: store-kojima/store01/RC-01/telemetry
{"message_id": "a3903cab-…", "gateway_id": "store01", "equipment_id": "RC-01", "kind": "showcase",
 "ts": "2026-10-15T12:38:54.307Z", "seq": 1792067936, "status": "ok",
 "metrics": {"run_status": 1, "setpoint_c": 5.0, "case_temp_c": 5.1, "defrost": 0, "door_open": 0, "alarm_code": 0}}
```

各項目には実務上の理由があります。

| 項目 | なぜ必要か |
| --- | --- |
| ポイントリスト(points.json) | アドレス・型・スケールをコードから分離。機器が増えてもコードを変えずに済む。店舗ごとに設備が違っても、ポイントリストの差し替えで対応できる |
| ts(UTC、末尾Z) | 日本時間で保存すると、海外拠点や他システムとの結合で破綻する。表示時にJSTへ変換する |
| seq(連番) | 欠損(飛び)の検出用 |
| message\_id | QoS1は「最低1回」なので重複があり得る。DB側で重複排除する鍵 |
| status | 通信エラーも「comm\_error」として送る。データが無い理由が後から分かる |
| トピック store-owner/店舗ゲートウェイ/機器/telemetry | IoTポリシーで「自分のトピックにだけ送れる」制限や、ルールでの振り分けに使う |
| SQLiteバッファ | 店舗の回線が切れている間は buffer.db に貯め、復旧後に古い順に再送。PUBACKが返った分だけ消す |

**やってみる(1台だけの故障)**:ショーケースだけが応答しなくなった状態を作ります。

1. ターミナル1を Ctrl+C で止め、RC-01 以外を起動し直します。

   ```
   python simulator/run_store.py --except RC-01
   ```
2. ターミナル3で、RC-01 だけを個別に起動します。

   ```
   python simulator/showcase.py
   ```
3. ターミナル2で `python gateway/gateway.py --console` を動かしたまま、ターミナル3の showcase.py を Ctrl+C で止めます。RC-01 の status だけが comm\_error に変わり、AC-01・PM-01・REF-01 は ok のまま読み続けることを確認します。showcase.py を再起動すると ok に戻ります。

1台が応答しなくても他の機器を読み続けられるのは、ゲートウェイが機器ごとに接続を持ち、1台の通信エラーを「その機器の comm\_error というデータ」として送って次の機器に進むからです。

## ステップ3:AWS IoT Coreへ送る

setup\_aws.py を1回実行すると、AWS側の受け皿づくりと証明書の発行、ゲートウェイ設定ファイルの作成までが自動で終わります。

1. AWS環境を作ります(1〜3分)。`--owner` には準備で決めた自分の名前を入れます。

   ```
   python aws/setup_aws.py --owner kojima
   ```

   中では次のことが起きています。
   - CloudFormationで、S3バケット、IoTのモノとポリシー、トピックルール、Glueテーブル、Athenaワークグループを作成
   - X.509証明書と秘密鍵を発行し、gateway/certs/ に保存。証明書をポリシーとモノに紐づけ
   - IoT Coreの接続先(エンドポイント)を調べ、gateway/gateway\_config.json を作成。owner もここに保存されるので、2回目以降の setup\_aws.py や他のスクリプトでは `--owner` を省略できます
2. AWSコンソールで **AWS IoT → MQTTテストクライアント** を開き、`store-kojima/#`(kojima は自分の owner)をサブスクライブします。
3. ゲートウェイを送信モードで起動します。

   ```
   python gateway/gateway.py
   ```

   ログに「MQTT接続: Success」「送信 4 件 / バッファ残 0 件」が出て、テストクライアントにJSONが届けば成功です。

ここで押さえる知識は次のとおりです。

- **証明書認証**:ID/パスワードではなく、ゲートウェイごとの証明書でTLS接続します。秘密鍵(private.pem.key)が漏れるとなりすましされるので、Gitや共有フォルダに置きません。
- **最小権限のポリシー**:ゲートウェイは「client ID が自分のモノの名前のときだけ接続できる」「store-kojima/store01/ 以下にだけ送れる」。試しに gateway\_config.json の topic\_prefix を変えると、送信が拒否され切断されるのが分かります。
- **ルールエンジン**:`SELECT *, timestamp() AS received_at_ms FROM 'store-kojima/+/+/telemetry'` で全機器のメッセージを拾い、AWSで受け取った時刻を足してS3に1件1ファイルで保存します。保存に失敗したものは errors/ に退避されます(デッドレターの考え方)。

### 命名のきまり(チームの共用アカウント)

同じAWSアカウントのIoT Coreは、チーム全員で1つのMQTTブローカーを共有しています。トピックに owner が入っていないと、他の人のルールが自分のデータまで拾ってしまいます。そのため、名前は次のように決めています(aws/naming.py と aws/template.yaml)。

| もの | 名前(owner が kojima の場合) |
| --- | --- |
| CloudFormationスタック | xcp-store-iot-kojima |
| 各リソース(S3、IAM、Lambda、DynamoDBなど) | xcp-store-iot-kojima-…(例:S3は xcp-store-iot-kojima-<アカウントID>) |
| IoTのモノ・ポリシー | xcp-store-iot-kojima-store01、xcp-store-iot-kojima-store01-policy |
| Glueデータベース・IoTルール(ハイフンが使えないもの) | xcp\_store\_iot\_kojima、xcp\_store\_iot\_kojima\_telemetry\_to\_s3 |
| CloudWatch Logsのロググループ | /xcp/store-iot/kojima/… |
| MQTTトピック | store-kojima/store01/機器ID/telemetry |
| タグ(スタックから全リソースへ) | Team=xcp、Project=store-iot、Env=poc、Owner=kojima |

AWSコンソールで `xcp-store-iot-` で検索すると、チームのリソースだけが見つかります。Cost Explorer では Owner タグで「誰の検証にいくらかかったか」を分けられます(タグをコスト配分タグとして有効にする必要があります)。

## ステップ4:S3とAthenaで分析する

データはS3の `raw/dt=YYYY-MM-DD/` に溜まり、AthenaのSQLでそのまま検索できます。サーバーを立てない「データレイク」型の構成です。

1. S3コンソールで、setup\_aws.py が表示したバケットの raw/ を開き、日付フォルダとJSONファイルができていることを確認します。
2. Athenaコンソールを開き、ワークグループを **xcp-store-iot-kojima**、データベースを **xcp\_store\_iot\_kojima** に切り替えます(kojima は自分の owner。結果の保存先は設定済み)。
3. aws/queries.sql のクエリを上から順に実行します。

| クエリ | 見るもの |
| --- | --- |
| 1. 届いたデータ | 生データの形 |
| 2. 庫内温度の時系列 | map型の metrics から値を取り出す方法。霜取り中(defrost=1)に温度が上がる様子 |
| 3. HACCPの温度記録 | 1時間ごとの最高・最低・平均(ダウンサンプリング)。紙の温度記録表をデータから作る |
| 4. 送信遅延 | ts(読んだ時刻)と received\_at\_ms(届いた時刻)の差 |
| 5. 欠損 | seq の飛び |
| 6. 重複 | 同じ message\_id の重複 |
| 7. エラー集計 | comm\_error と異常コードの件数 |
| 8. 電力のデマンド | 30分ごとの使用電力量。積算値の差分で使用量を出す |
| 9. 冷凍機の発停回数 | 1時間あたりの発停。保守で見る値 |

注意点が2つあります。

- **dt はUTCの日付**です。日本時間の0時〜9時のデータは前日の dt に入ります。店舗の営業日で集計するときは、dt を前日と当日の2日分にして、時刻をJSTに変換してから絞ります。
- Athenaは**読んだデータ量で課金**されます(ワークグループで1クエリ1GBまでに制限済み)。必ず `WHERE dt = …` で日付を絞る習慣をつけてください。学習規模ならほぼ0円です。

## ステップ5:障害を起こして学ぶ

実務で差がつくのは「うまくいかないとき」の設計です。わざと障害を起こし、データにどう表れるかをAthenaで確かめます。店舗では、夜間の回線工事やルーターの再起動、バックヤードのゲートウェイの電源が抜かれる、といったことが実際に起きます。

| 実験 | やり方 | 期待される結果 | 確認クエリ |
| --- | --- | --- | --- |
| 回線断 | ゲートウェイ起動中にPCのWi‑Fiを1〜2分切り、戻す | ログで「バッファ残」が増え、復旧後にまとめて送信。データは欠けない | 4(遅延が大きい行が出る) |
| 機器停止 | `python simulator/run_store.py --except RC-01` と `python simulator/showcase.py` で起動しておき、showcase.py だけを Ctrl+C で止める。1分後に再起動 | その間、RC-01 だけ status = comm\_error のメッセージが届く。他の機器のデータは欠けない | 7 |
| ゲートウェイ停止 | gateway.py を止めて1分後に再起動 | その間のデータは存在しない(バッファにも無い) | 5(seq の飛び) |
| 重複 | 送信直後に回線を切るなどPUBACKを取りこぼす | 同じ message\_id が2件届くことがある | 6 |
| 権限外送信 | topic\_prefix を変えて送る | 接続が切られ、データは届かない | なし(ログで確認) |

ゲートウェイ停止時の欠損は、このキットでは防げません。実務ではゲートウェイ自体の死活監視(一定時間データが来なければアラート)で検知します(ハンズオン4で作ります)。重複は、DBに入れる段階で message\_id(または機器ID+時刻)を主キーにしたUPSERTで吸収するのが定石です。

ショーケースの温度記録では、欠損は「記録が無い時間帯」として監査で問題になります。実験のたびに「どの障害が、どのクエリで、どう見えるか」をメモしておくと、そのまま監視設計の叩き台になります。

## 片付け・トラブル対応・次のステップ

学習が一区切りしたら、次のコマンドでAWS側をすべて削除します。証明書の無効化・削除、S3の中身の削除、スタック削除、ローカルの証明書削除まで自動で行います。消すのは自分の owner のスタックだけです。再開するときは setup\_aws.py をもう一度実行するだけです。

```
python aws/teardown_aws.py
```

作るものはすべて従量課金で、起動しっぱなしで課金されるサービス(RDS、Timestream for InfluxDB、NATゲートウェイなど)は含みません。費用の大半は、メッセージを1件ずつS3に保存するときのPUT料金と、IoT Coreのメッセージ数です。どちらも件数に比例するので、送信周期を10秒より短くしないのが節約のコツです。ハンズオン全体の構成図と費用の内訳は[アーキテクチャとコスト](./アーキテクチャとコスト.md)にまとめています。

### よくあるつまずき

| 症状 | 原因と対処 |
| --- | --- |
| シミュレータ起動で Address already in use | 5021〜5023・5010番ポートが使用中。前に起動したシミュレータが残っていないか確認する。別のポートを使う場合は `python simulator/showcase.py --port 5032` のように起動し、points.json のその機器の port も合わせる |
| setup\_aws.py が「--owner を指定してください」 | 初回は `--owner 自分の名前` が必要。英小文字と数字だけ、16文字以内 |
| setup\_aws.py が「owner=… で作られています」 | gateway\_config.json と違う owner を指定した。別の owner で作り直すときは、先に teardown\_aws.py で今のスタックを消す |
| setup\_aws.py で「already exists」 | S3バケット・IAMロールなどの名前が他の人と重なっている。owner がチーム内で重複していないか確認する |
| ゲートウェイが接続と切断を繰り返す | client\_id や topic がポリシーと不一致、または証明書が未アタッチ。setup\_aws.py を再実行 |
| MQTT接続でSSLエラー | 社内プロキシやセキュリティソフトが8883番ポートを遮断。自宅回線やテザリングで試す |
| Athenaで0件 | ワークグループとデータベースが自分の owner のものか確認。dt がUTCの日付か確認。S3の raw/ にファイルがあるか確認 |
| S3に何も来ない | errors/ にファイルがあればルールの保存失敗。IoT Coreのルール画面でエラーを確認 |
| setup\_aws.py で権限エラー | 作業ユーザーにCloudFormation・IoT・IAM・S3・Glue・Athenaの権限が必要。IAMロールに名前を付けるので、CAPABILITY\_NAMED\_IAM でのスタック作成が許可されている必要がある |
