# IoT学習ハンズオン6:入店カウンタとPOS

Oct 15, 2026 · @Reo Kojima

前提:[IoT学習ハンズオン PC+シミュレータ+AWS](./IoT学習ハンズオン%20PC%2Bシミュレータ%2BAWS.md)のステップ1〜4が終わっていて、Athenaでテレメトリが見えることです(ハンズオン2〜5は必須ではありません)。所要時間は60〜90分です。費用は数時間の学習なら数円、1か月つけっぱなしにしても追加は月百円程度です(詳しくは最後の「費用」)。

## 全体像

ここまでのデータは、すべて店舗の**設備**(空調・ショーケース・電力計・冷凍機盤)からModbusやMCプロトコルで読んだものでした。店舗で扱うデータは設備だけではありません。「何人来て、何人が買って、いくら売れたか」は、入店カウンタやPOS(レジ)といった**店舗のシステム**が持っています。今回は、この2つのシステムからデータを取り込み、設備のデータと同じ流れでAWSに貯めます。

| データ源 | 模擬するもの | つなぎ方 | 取り方 |
| --- | --- | --- | --- |
| 入店カウンタ PC-01 | 出入口の天井のセンサー。メーカーのREST APIで1分ごとの入店数・退店数を返す | HTTP(APIキーで認証) | 前回取った**時刻**の続きから |
| POS | 店舗サーバー(ストアサーバー)のDB。レジで会計するたびに取引が1行増える | DBに読み取り専用で接続 | 前回取った**取引番号**の続きから |

```
入店カウンタ(HTTP API) ──GET /api/v1/counts?since=…──┐
                                                         ├─ 店舗ゲートウェイ ── MQTT ─→ IoT Core ─┬→ ルール ─→ S3 people/ → Athena people_count
店舗サーバー(POSのDB)  ──SELECT … WHERE txn_id > …──┘   (どこまで取ったかを記録)               └→ ルール ─→ S3 pos/    → Athena pos_transactions
```

| 追加するもの | 役割 | 学べること |
| --- | --- | --- |
| simulator/people\_counter.py | 入店カウンタのREST APIを模擬(ポート8081) | APIキー、HTTPのステータスコード、ページング |
| simulator/pos\_server.py | 店舗サーバーのDB(SQLite:simulator/data/pos.db)に取引を書き続ける | POSのテーブル、取消、現地時刻だけの時刻 |
| simulator/store\_model.py | 来店と会計のモデル、商品マスタ(店内コードのJAN) | 別々のシステムの数字がつながる理由 |
| gateway/sources.py | 入店カウンタとPOSから差分を取る | ウォーターマーク、冪等な取り直し、読み取り専用の接続 |
| gateway/sources.json | 店舗のシステムの接続先(最初は enabled: false) | 接続先・秘密情報をコードから分ける |
| aws/template.yaml の PeopleCountToS3Rule / PosTxnToS3Rule と2つのGlueテーブル | トピックごとにS3の別の場所へ保存し、Athenaのテーブルにする | 種類の違うデータを分けて貯める |
| aws/queries.sql の10〜15番 | 来店客数、売上・客数・客単価、買上率、売れ筋、遅延、欠番 | 別々のシステムのデータを時刻で突き合わせる |

## 設備とシステムの違い:「今の値」と「増えた分」

設備から読むのは「今の室温」「今の積算電力量」のような**今の値**です。読み逃しても、次に読めば最新の値が分かります。

店舗のシステムが持っているのは「12時03分の1分間に5人入店」「取引番号1234:牛乳と食パンで406円」のような**出来事の記録**です。1件でも取り逃せば売上が合わなくなり、2回取れば売上が二重になります。そこで、システムからは次の考え方で取ります。

| 考え方 | 内容 | このキットでの実装 |
| --- | --- | --- |
| ウォーターマーク | 「どこまで取ったか」の印を覚えておき、次はその続きから取る | buffer.db の watermarks テーブル(ソースごとに1行) |
| 印は送信バッファと一緒に進める | 取ったデータをバッファに積むことと、印を進めることを1つのトランザクションで行う | Buffer.put\_with\_watermark()。途中で落ちても「積んだのに印が進まない(二重取り)」「印だけ進む(取りこぼし)」が起きない |
| 取れなかったら印を進めない | APIのエラーやDBに接続できないときは、何も積まず、次の周期で同じところから取り直す | sources.py が例外を出し、ゲートウェイは次の周期へ |
| 二重に届いても困らない | QoS1や取り直しで同じデータが2回届くことはある。集計する側で自然なキー(センサー+時刻、店舗+取引番号)で重複を除く | queries.sql の10・11番 |

### 入店カウンタ:時刻のウォーターマーク

入店カウンタのAPIは、`since`(この時刻以降)を指定すると、**締まった**1分ごとの集計を古い順に返します。今まさに数えている途中の1分は返しません。返ってきた `next_since` を次の `since` に使えば、取りこぼしも重複もありません。長く止まっていた後は `has_more: true` が返るので、続けて問い合わせます(1周期で取るのは最大5ページ、つまり5時間分までにして、ゲートウェイの周期が長引かないようにしています)。

メーカーの項目名 `in` / `out` は、ゲートウェイで `in_count` / `out_count` に付け替えてから送ります。`in` はSQLの予約語なので、そのままだとAthenaで扱いにくいためです。項目名を自分たちの決まりにそろえるのも、システム連携でよくある仕事です。

### POS:取引番号のウォーターマーク

POSの取引には「取引番号(txn\_id)」と「会計した時刻(sold\_at)」があります。差分をどちらで取るかが、このハンズオンの一番大事なところです。

シミュレータのセルフレジ(4番)は、店舗サーバーとの通信が不安定な想定で、取引を手元に貯めて**10分ごとにまとめて**書きます。そのため、12:05に会計した取引が、12:09に会計した有人レジの取引より**後に**DBに書かれます。

| 差分の取り方 | 12:10 に「前回(12:09)より後」を取ると | 結果 |
| --- | --- | --- |
| 時刻(sold\_at > 12:09) | 12:05 のセルフレジの取引は「前回より前」なので取らない | **取りこぼす** |
| 取引番号(txn\_id > 前回の最後の番号) | DBに書かれた順に番号が増えるので、遅れて書かれた取引も新しい番号を持つ | 取りこぼさない |

「DBに書かれた順に増える値」で取るのが原則です。実際のシステムでは、連番の代わりに「更新日時」の列や、DBの変更履歴(CDC)を使うこともあります。どれを使う場合も、「後から書かれる行がないか」をベンダーに確認することが欠かせません。

ほかにも、POS連携でよく出会う点を入れています。

- **POSの時刻はタイムゾーンなし**:sold\_at は `2026-10-15 21:34:05` のような日本時間の現地時刻で、タイムゾーンが書かれていません。ゲートウェイでUTCに直してから送ります(ハンズオン1の「時刻は必ずUTCで持つ」)。
- **取消(VOID)**:打ち間違いなどで取引を取り消すと、元の取引を打ち消すマイナスの取引が増えます。元の取引は消えません。売上は「足せば打ち消される」ので、客数を数えるときだけ取消の件数を引きます。
- **読み取り専用で接続し、すぐ切る**:連携のせいでPOSのデータを壊したり、レジを待たせたりしてはいけません。読み取り専用で開き、読み終わったら接続を閉じます。シミュレータのDBは、読む側がいても書く側が待たされないWALモードにしています。実際のPOSでは、ベンダーが連携用に用意した読み取り専用のユーザーとビューを使います。

## ステップ1:シミュレータを起動して、APIとDBをのぞく

1. ターミナル1で、店舗の設備とシステムのシミュレータをまとめて起動します。入店カウンタ(PC-01)と店舗サーバー(POS)も一緒に起動します。

   ```
   python simulator/run_store.py --verbose
   ```

   初めて起動したときは、POSの店舗サーバーが過去2時間分の取引を作ってから、1分ごとに取引を書いていきます。`[POS   ] 22:15 取引 1 件を書き込み(セルフレジ保留 6 件)` のような行が出ます。
2. ターミナル2で、入店カウンタのAPIを直接呼んでみます。まずはAPIキーなしです。

   ```
   curl.exe -i "http://127.0.0.1:8081/api/v1/counts"
   ```

   `401 Unauthorized` が返ります。次にAPIキーを付けます(PowerShellでは `curl` ではなく `curl.exe` と打ちます)。

   ```
   curl.exe -H "X-API-Key: demo-key-store01" "http://127.0.0.1:8081/api/v1/counts?limit=3"
   ```

   次のような応答が返ります(値は一例)。

   ```
   {"sensor_id": "ENT-01", "bins": [{"start": "2026-10-15T13:00:00Z", "end": "2026-10-15T13:01:00Z", "in": 1, "out": 2}, …],
    "next_since": "2026-10-15T13:03:00Z", "has_more": true}
   ```
3. POSのDBの中身を見ます。

   ```
   python -c "import sqlite3; db = sqlite3.connect('file:simulator/data/pos.db?mode=ro', uri=True); [print(r) for r in db.execute('SELECT * FROM pos_transaction ORDER BY txn_id DESC LIMIT 5')]"
   ```

   `(286, 'S001', 1, '2026-10-15 22:15:08', 'SALE', None, 286, 2)` のように、取引番号・店舗コード・レジ番号・会計時刻(日本時間)・種類・取消元・金額・点数が並びます。

## ステップ2:ゲートウェイで取り込む

1. `gateway/sources.json` を開き、PC-01 と POS の `"enabled": false` を両方 `true` にして保存します。
2. 画面表示モードで1回動かします。

   ```
   python gateway/gateway.py --console --once
   ```

   ログに次の2行が出ます(件数は一例)。1回目は印が無いので、入店カウンタは過去2時間分、POSは最初の200件(1周期の上限)を取ります。

   ```
   INFO PC-01: 120件を取得(ウォーターマーク None → 2026-10-15T13:19:00Z)
   INFO POS: 200件を取得(ウォーターマーク None → 200)
   ```
3. AWSへ送ります。`setup_aws.py` を再実行して、ルールとGlueテーブルを追加してから、ゲートウェイを起動します。

   ```
   python aws/setup_aws.py
   python gateway/gateway.py
   ```

   2周期目以降は、入店カウンタは1分に1件、POSは増えた取引だけを取ります。ログの「ウォーターマーク 200 → 286」のような行で、印が進んでいく様子が見えます。
4. AWSコンソールの **MQTTテストクライアント** で `store-kojima/store01/POS/#` をサブスクライブすると、取引が明細付きのJSONで届くのが見えます(kojima は自分の owner)。
5. ゲートウェイを Ctrl+C で止めて1〜2分待ち、もう一度起動します。止めていた間の分が、ちょうど続きから取られることを確認します(印は buffer.db に保存されているので、再起動しても続きから取れます)。

## ステップ3:Athenaで店舗の数字を見る

aws/queries.sql の10番以降を実行します。

| クエリ | 見るもの |
| --- | --- |
| 10. 来店客数 | 1時間ごとの入店数。昼と夕方にピークがある |
| 11. 売上・客数・客単価 | 取引番号で重複を除き、取消を打ち消してから集計する |
| 12. 買上率 | 客数 ÷ 来店客数。入店カウンタとPOSという別々のシステムを、日本時間の1時間で突き合わせる。シミュレータでは60%台になる |
| 13. 売れ筋 | 明細(items)の配列を UNNEST で展開し、商品ごとに集計する |
| 14. レジごとの遅延 | セルフレジ(4番)だけ、会計からAWSに届くまでが数分遅い |
| 15. 欠番 | 取引番号の飛び。0件なら取りこぼしは無い |

**店舗の数字は日本時間の1日で見る**:dt はAWSが受け取った日(UTC)です。日本時間の0時〜9時はUTCでは前日なので、10番以降のクエリは dt を前日と当日の2日分にしてから、時刻を日本時間に直して「今日」に絞っています。設備の温度記録(3番)よりも、売上は「何日の売上か」がずれると大きな問題になります。

**買上率は、別々のシステムをつなぐと初めて分かる数字**です。入店カウンタだけでは「何人来たか」、POSだけでは「何人買ったか」しか分かりません。店舗運営では、来店客数が多いのに買上率が低い時間帯は、品切れやレジ待ちを疑う、といった使い方をします。

## ステップ4:やってみる

| 実験 | 操作 | 期待される結果 |
| --- | --- | --- |
| 時刻で差分を取ったら | クエリ14で、セルフレジの遅延が数分あることを確かめる。この遅延より短い間隔で「前回の時刻より後」を取ると、どうなるかを考える | 遅れて書かれたセルフレジの取引を取りこぼす。取引番号で取っているので、クエリ15の欠番は0件のまま |
| APIの一時的なエラー | ターミナル1を止め、`python simulator/run_store.py --except PC-01` で起動し直し、別のターミナルで `python simulator/people_counter.py --fail-rate 0.5` を起動する | ゲートウェイのログに「エラーを返しました(503)。次の周期で取り直します」が時々出るが、印は進まないので、クエリ10の1分ごとの集計は欠けない |
| APIキーの間違い | sources.json の api\_key を書き換えてゲートウェイを再起動する | 「APIキーが違います(401)」が出続ける。取り直しても直らないエラーなので、設定を直すまで直らない(一時的なエラーとの違い) |
| POSが止まる | `run_store.py --except POS` と `python simulator/pos_server.py` で起動しておき、pos\_server.py を数分止めてから再開する | 止めていた間の取引は、再開したときにまとめて書かれ、ゲートウェイも続きから取る。クエリ15の欠番は0件 |
| 二重に送る | ゲートウェイを止め、buffer.db の watermarks テーブルから POS の行を消して再起動する(印を失った状態) | 取引番号1から取り直すので、同じ取引が2回届く。クエリ11は取引番号で重複を除いているので売上は変わらない。重複を除かない `SELECT sum(total_yen) FROM pos_transactions WHERE …` は増える |

印を消す操作は次のとおりです(ゲートウェイを止めてから実行します)。

```
python -c "import sqlite3; db = sqlite3.connect('gateway/buffer.db'); db.execute('DELETE FROM watermarks WHERE source_id = ?', ('POS',)); db.commit()"
```

## 片付け

```
python aws/teardown_aws.py
```

ルールとGlueテーブルもスタックごと削除されます。店舗サーバーのDB(`simulator/data/pos.db`)はローカルに残ります。消すと、次に起動したときに過去2時間分から作り直されます。そのときは buffer.db の POS の印も消してください(番号が1から振り直されるため)。

## よくあるつまずき

| 症状 | 原因と対処 |
| --- | --- |
| ゲートウェイのログに「店舗システム=なし」 | sources.json の enabled が false のまま |
| 「入店カウンタのAPIに接続できません」 | people\_counter.py が動いていない(run\_store.py で起動したか確認)。8081番ポートが他で使われている場合は `--port` で変え、sources.json の url も合わせる |
| 「POSのDBが見つかりません」 | pos\_server.py をまだ起動していない(初回起動でDBが作られる) |
| `curl` で「Invoke-WebRequest」のエラー | PowerShellの `curl` は別のコマンドの別名。`curl.exe` と打つ |
| Athenaで people\_count / pos\_transactions が0件 | `setup_aws.py` を再実行していない(ルールとテーブルが無い)。S3の people/ と pos/ にファイルがあるか確認 |
| 買上率が100%を超える時間帯がある | 入店してから会計するまで15分かかるので、時間帯の境目で「前の時間に入った人の会計」が入る。1時間単位の買上率は目安として見る |
| POSのDBを消したら、取引が届かなくなった | 取引番号が1から振り直されたのに、ゲートウェイの印が古い番号のまま。buffer.db の POS の印を消す(ステップ4の操作) |
