# IoT学習ハンズオン7:在庫連携と突き合わせ分析

Oct 15, 2026 · @Reo Kojima

前提:[IoT学習ハンズオン6 入店カウンタとPOS](./IoT学習ハンズオン6%20入店カウンタとPOS.md)が終わっていて、Athenaで pos\_transactions と people\_count が見えることです。所要時間は60〜90分です。費用は数時間の学習なら数円、1か月つけっぱなしにしても追加は月数十円です(詳しくは最後の「費用」)。

## 全体像

最後に、在庫・発注システムのデータを取り込みます。このシステムは、ここまでのどれとも違う「**ファイル連携**」でデータを出します。決まった時刻に在庫の一覧をCSVファイルに書き出し、受け取る側がそれを取りに行く方式です。基幹システムとの連携では、今でもいちばんよく見かける形です。

そのうえで、設備・入店カウンタ・POS・在庫という**4つの経路から来たデータを突き合わせて**、店舗の1日を1つの表にします。

```
在庫・発注システム ──(10分ごとにCSVを書き出す)──→ outbox/
                                                      │
店舗ゲートウェイ ── ①検証(文字コード・見出し・件数) ── ②変換(UTF-8・英語の列名・UTC) ──┐
       │                                                                              │
       └─ ③証明書で一時的な認証情報をもらう(IoT credential provider)                  │
                                                                                      ▼
                                       S3 inventory-raw/(原本)・inventory/dt=…/(変換後) → Athena inventory_snapshot
```

| 追加するもの | 役割 | 学べること |
| --- | --- | --- |
| simulator/inventory\_system.py | POSの売上で在庫を減らし、発注点を割ったら発注、2時間後に入荷。10分ごとに在庫一覧をCSVに書き出す | 古い基幹システムのCSVの形(Shift\_JIS、日本語の見出し、件数の行) |
| gateway/files.py | CSVを検証・変換してS3にアップロードする | 受け取る側の検証、原本を残す、やり直しても二重にならないキー |
| gateway/sources.json の INV | 在庫CSVの出力フォルダ(最初は enabled: false) | |
| aws/template.yaml の FilesRole / FilesRoleAlias | ゲートウェイが証明書で使えるIAMロール(在庫ファイルの書き込みだけ)と、その窓口(ロールエイリアス) | 機器に長期のアクセスキーを置かない |
| aws/template.yaml の GatewayPolicy | ゲートウェイがこのロールエイリアスだけを使える権限を追加 | |
| aws/template.yaml の InventoryTable | inventory\_snapshot テーブル(CSV) | CSVをAthenaで読む |
| aws/queries.sql の16〜19番 | 在庫日数、発注点割れ、温度逸脱×在庫金額、店舗の1日 | 別々の経路のデータを時刻とキーで突き合わせる |

## ファイル連携で押さえること

在庫・発注システムが書き出すCSVは、次のような形です(Shift\_JISで保存されています)。

```
店舗コード,JANコード,商品名,部門,陳列場所,売価,在庫数,発注点,発注数,入荷予定日時,在庫日時
S001,2000000000015,牛乳 1000ml,日配,RC-01,238,419,210,0,,2026/10/15 22:31
S001,2000000000022,ヨーグルト 400g,日配,RC-01,158,278,140,0,,2026/10/15 22:31
…
END,20
```

### 出す側と受け取る側の約束

ファイル連携は、出す側と受け取る側が「ファイルの置き方」を約束しておかないと、事故が起きます。このキットでは次の約束にしています。

| 約束 | 何を防ぐか | 実装 |
| --- | --- | --- |
| 書き終わってから名前を変える | 書きかけのファイルを読んでしまう | 在庫システムは `.csv.tmp` で書き、書き終わったら `.csv` に名前を変える。ゲートウェイは `.csv` だけを読む |
| 最後の行に件数を書く(トレーラー) | 途中で切れたファイルを、正しいものとして取り込んでしまう | `END,20` の件数と明細の行数を照合する |
| 処理済みのファイルは移す | 同じファイルを何度も取り込む、どれが済んだか分からない | アップロードできたら `sent/`、受け付けなかったら `error/` に移す。どちらでもなければ次の周期でやり直す |

### 受け取る側の検証と変換

ゲートウェイ(gateway/files.py)は、1つでもおかしなところがあれば**アップロードしません**。中途半端なデータが分析に混ざると、後から見つけて取り除くのは大変だからです。

| 検証 | 例 |
| --- | --- |
| 文字コード | Shift\_JISとして読めるか(UTF-8で出されたら受け付けない) |
| 見出し | 列の名前と順番が仕様どおりか(システムの改修で列が増えた・名前が変わった、に気づける) |
| 列数と数値 | 各行の列数がそろっているか、在庫数などが数字か |
| 件数 | END行の件数と明細の行数が一致するか |

検証に通ったら、分析しやすい形に変換します。

- 文字コードを **UTF-8** に、改行を LF に変える(Athenaは Shift\_JIS を読めない)
- 見出しを英語の列名(store\_code、jan、stock\_qty …)に付け替える
- 日時 `2026/10/15 22:31`(日本時間、タイムゾーンなし)を UTC の `2026-10-15T13:31:00.000Z` に直す(ハンズオン1・6と同じ決まり)

### 原本を残す、やり直しても二重にならない

アップロードは2つです。変換前の**原本**を `inventory-raw/` に、変換後を `inventory/dt=日付/` に置きます。変換のしかたに誤りが見つかっても、原本があれば作り直せます。

S3のキー(ファイル名)は「在庫日時の日付」と「元のファイル名」だけから決まります。アップロードの途中で回線が切れて、同じファイルをもう一度アップロードしても、同じキーに上書きされるだけです。MQTTのメッセージ(同じものが2回届くと2件になる)と違い、**やり直しても二重になりません**。日付に「アップロードした日」を使わないのもこのためです(日付をまたいでやり直すと、別の日の場所に2つできてしまう)。

### 機器に長期のアクセスキーを置かない

S3にアップロードするにはAWSの認証情報が要ります。ハンズオン2のGrafanaにはアクセスキー(期限のない長期の認証情報)を渡しましたが、店舗に置くゲートウェイにはそうしません。店舗の機器は盗まれたり、退役した後に捨てられたりするからです。

代わりに、ゲートウェイが既に持っている**X.509証明書**を使います。AWS IoT の credential provider に証明書を見せると、決められたIAMロールの**一時的な認証情報**(1時間で失効)がもらえます。

| もの | 内容 |
| --- | --- |
| FilesRole(IAMロール) | S3の inventory/ と inventory-raw/ への書き込み(PutObject)だけを許可。読み取りも削除もできない |
| FilesRoleAlias(ロールエイリアス) | 証明書からこのロールを使うための窓口。認証情報の有効期間(1時間)もここで決める |
| GatewayPolicy への追加 | このゲートウェイの証明書が、このロールエイリアスだけを使える(`iot:AssumeRoleWithCertificate`) |

証明書を失効させれば、一時的な認証情報ももらえなくなります。機器の認証を証明書1つにまとめておくと、止めるときも1か所で済みます。

## ステップ1:AWS環境とゲートウェイの設定を更新する

1. `setup_aws.py` を再実行します。ロール・ロールエイリアス・在庫テーブルが追加され、gateway/gateway\_config.json にファイル連携の設定(credential provider の接続先、ロールエイリアス、バケット)が書き足されます。

   ```
   python aws/setup_aws.py
   ```
2. `gateway/sources.json` を開き、INV の `"enabled": false` を `true` にします(PC-01 と POS はハンズオン6で true にしたままにします)。

## ステップ2:在庫のCSVを書き出して、検証だけしてみる

1. ターミナル1でシミュレータを起動し直します。在庫・発注システム(INV)も一緒に起動します。

   ```
   python simulator/run_store.py
   ```

   `[INV   ] 取引 12 件を反映し、stock_S001_20261015_2230.csv を書き出しました` のような行が10分ごとに出ます(起動直後にも1回書き出します)。初めて起動したときは、その時点の在庫数で棚卸しをしたことにして、それより後のPOSの取引だけを在庫に反映します。
2. `simulator/data/outbox/` を開き、CSVファイルができていることを確かめます。メモ帳で開くと、Shift\_JISなので文字化けすることがあります(Excelでは読めます)。
3. ターミナル2で、ゲートウェイを画面表示モードで1回動かします。画面表示モードでは、検証と変換だけを行い、アップロードもファイルの移動もしません。

   ```
   python gateway/gateway.py --console --once
   ```

   次のように、変換後の内容とアップロード先のキーが表示されます。

   ```
   [console] stock_S001_20261015_2230.csv → s3://…/inventory/dt=2026-10-15/store01-stock_S001_20261015_2230.csv(20行)
   store_code,jan,product_name,category,location,price_yen,stock_qty,reorder_point,order_qty,arrival_due,snapshot_at
   S001,2000000000015,牛乳 1000ml,日配,RC-01,238,419,210,0,,2026-10-15T13:30:00.000Z
   ```

## ステップ3:S3にアップロードする

1. ゲートウェイを送信モードで起動します。

   ```
   python gateway/gateway.py
   ```

   ログに次の行が出ます。

   ```
   INFO 一時的な認証情報を取得しました(失効 2026-10-15T14:31:02Z)
   INFO INV stock_S001_20261015_2230.csv をアップロードしました → inventory/dt=2026-10-15/store01-stock_S001_20261015_2230.csv
   ```

   一時的な認証情報は失効の5分前まで使い回すので、取得のログは1時間に1回程度しか出ません。
2. `simulator/data/outbox/sent/` にファイルが移ったことを確かめます。
3. S3コンソールで、バケットの `inventory-raw/store01/`(原本)と `inventory/dt=…/`(変換後)の両方にファイルがあることを確かめます。

## ステップ4:突き合わせて分析する

aws/queries.sql の16番以降を実行します。

| クエリ | 見るもの | つないでいるデータ |
| --- | --- | --- |
| 16. 在庫日数 | 今の在庫が、直近24時間の売れ方で何日もつか。小さい順=欠品が近い順 | 在庫(CSV)× POS |
| 17. 発注点割れ | 発注点を割っている商品と入荷予定 | 在庫(CSV) |
| 18. 温度逸脱×在庫 | ショーケースRC-01が10℃を超えていた10分間ごとに、そのケースに並んでいた商品の在庫数と在庫金額 | 設備(Modbus)× 在庫(CSV)× 棚割(陳列場所) |
| 19. 店舗の1日 | 1時間ごとの来店客数・客数・売上・電力・室温・ショーケースの温度逸脱 | 入店カウンタ × POS × 設備 |

**18番を動かすには**、ハンズオン4と同じように扉を開けっ放しにして、10℃を超えた時間を作ります。

```
python simulator/force_alarm.py --door open
```

2〜3分待ってから `--door close` で閉め、在庫CSVの次の書き出し(10分ごと)とアップロードを待ってから18番を実行します。「この10分間に、冷蔵ケースには牛乳やヨーグルトが何個、いくら分並んでいたか」が出ます。温度逸脱の通知(ハンズオン4)を受けた店長が、「どの商品を確かめるべきか、最悪いくら分の廃棄になるか」を判断する材料です。設備のデータだけでも、在庫のデータだけでも出せない数字です。

**突き合わせの鍵は「時刻」と「コード」**です。

| 突き合わせ | 鍵 | 注意 |
| --- | --- | --- |
| 在庫 × POS | JANコード | システムごとにコードの持ち方が違うことがある(先頭の0の有無、店内コード)。このキットは同じ商品マスタから作っているのでそろっている |
| 設備 × 在庫 | 時刻(10分単位)と陳列場所(棚割) | 時刻はすべてUTCにそろえてある。棚割(どの商品がどの什器に並ぶか)は、在庫CSVの「陳列場所」列から |
| 入店 × POS × 設備 | 時刻(日本時間の1時間) | 店舗の1日は日本時間で区切る |

ハンズオン1から「時刻は必ずUTCで持つ」「機器・システムの値は自分たちの決めた名前にそろえる」としてきたのは、最後にこうして突き合わせるためです。

**突き合わせのクエリは高くつきやすい**:18・19番は、テレメトリ(機器4台×10秒ごと、1件1ファイル)を2日分読みます。Athenaはクエリのたびに全ファイルをS3から読むので、ファイルの数が多いほど高くなります。1回なら1円未満ですが、Grafanaのパネルにして30秒ごとに更新すると、ハンズオン2の注意と同じく、すぐに高くなります。実運用では、テレメトリを数分ぶんまとめて1ファイルにする(Amazon Data Firehose)、1時間ごとの集計テーブルを夜間に作っておく、といった工夫をします。

## ステップ5:やってみる

| 実験 | 操作 | 期待される結果 |
| --- | --- | --- |
| 途中で切れたファイル | 下の手順で、最後の行(END,件数)が無いCSVを outbox に置く | ゲートウェイのログに「最後の行が END,件数 ではありません(途中で切れている可能性)」が出て、ファイルは `error/` に移る。S3には何も増えない |
| 回線断 | ゲートウェイ起動中にPCのWi‑Fiを切り、在庫CSVの書き出しを1〜2回待ってから戻す | 回線が戻るまでCSVは outbox に残り、戻ったら古い順にアップロードされる(フォルダそのものがバッファになる) |
| やり直しても二重にならない | `sent/` のファイルを1つ outbox に戻す | 同じキーにもう一度アップロードされる(上書き)。Athenaの17番の結果は変わらない |
| 権限の外 | ロールで許可していない場所に書けないことを確かめる。gateway/files.py の `key = f"inventory/dt=…` を `f"raw/dt=…` に書き換えて動かす | `AccessDenied` でアップロードに失敗し、ファイルは outbox に残る。確かめたら元に戻す |
| 証明書を止める | AWS IoTコンソールで、ゲートウェイの証明書を「非アクティブ」にする | MQTTの接続も、一時的な認証情報の取得もできなくなる。証明書1つを止めれば、ゲートウェイのすべてのアクセスが止まる。確かめたら「アクティブ」に戻す |

途中で切れたCSVを置く手順は次のとおりです(在庫CSVを1つコピーし、最後の行を消します)。

```
python -c "import glob; f = sorted(glob.glob('simulator/data/outbox/sent/*.csv'))[-1]; b = open(f, 'rb').read(); open('simulator/data/outbox/broken.csv', 'wb').write(b[:b.rfind(b'END')])"
```

## 片付け

```
python aws/teardown_aws.py
```

ロール・ロールエイリアス・在庫テーブルもスタックごと削除されます。在庫・発注システムのデータ(`simulator/data/inventory.db` と `simulator/data/outbox/`)はローカルに残ります。消すと、次に起動したときに在庫数を初期値に戻して棚卸しからやり直します。

## よくあるつまずき

| 症状 | 原因と対処 |
| --- | --- |
| ゲートウェイの起動時に「ファイル連携の設定(aws)がありません」 | `setup_aws.py` を再実行していない。再実行すると gateway\_config.json に aws の設定が書き足される |
| 一時的な認証情報の取得で `403` | GatewayPolicy にロールエイリアスの権限が無い(`setup_aws.py` を再実行していない)、または証明書が非アクティブ |
| 一時的な認証情報の取得で SSL のエラー | gateway\_config.json の credentials\_endpoint が MQTT の接続先(…-ats.iot…)になっている。`setup_aws.py` を再実行する |
| アップロードで `AccessDenied` | FilesRole で許可していない場所に書こうとしている。キーが inventory/ か inventory-raw/ で始まっているか確認 |
| outbox にCSVができない | inventory\_system.py が「POSのDBがまだありません」と言っている。pos\_server.py を起動する |
| すべてのファイルが error/ に移る | 見出しや文字コードが仕様と違う。ログの理由を見る。inventory\_system.py を書き換えた場合は、files.py の COLUMNS と合っているか確認 |
| 16番の在庫日数がとても大きい | POSのデータが24時間分たまっていない(直近24時間の販売数が少なく出る)。1日動かすと落ち着く |
| 18番が0件 | 温度逸脱が起きていない、または逸脱した時間帯の在庫CSVがまだアップロードされていない。扉を開けっ放しにしてから、次の書き出し(10分ごと)を待つ |
