# 作業手順（AWS での動作確認）

`factory-replay` を自分の AWS 環境に作り、①〜④ が動くことを確認して、最後に片付けるまでの手順。
上から順に進めれば、初めての人でも 1 時間ほどで一通り確認できる。

- 設計・方針: [実現方針.md](実現方針.md)
- コマンドやファイルの説明: [factory-replay/README.md](../README.md)

コマンドはすべて **PowerShell で `factory-replay` フォルダから** 実行する。
`<owner>` は自分の名前（英小文字で始まる英小文字・数字 2〜16 文字。例: `kojima`）に置き換える。

| 章 | 内容 | 所要時間 |
|---|---|---|
| 0 | 事前準備（初回のみ） | 10 分 |
| 1 | 毎回の準備（仮想環境・ログイン・変数） | 1 分 |
| 2 | ① サンプル CSV を確認する（AWS 不要） | 1 分 |
| 3 | AWS 環境を作る | 15 分 |
| 4 | ② アップロードして少しずつ反映させる | 5〜30 分 |
| 5 | ③ HTTP API で取得する（Postman / CLI） | 10 分 |
| 6 | ④ リセットする | 10 分 |
| 7 | （任意）異常系・大きいデータ | 20 分 |
| 8 | 後片付け | 10 分 |

## 0. 事前準備（初回のみ）

| 必要なもの | 確認コマンド・入手先 |
|---|---|
| Python 3.10 以上 | `python --version` |
| AWS CLI v2 | `aws --version` |
| Postman（デスクトップアプリ） | 5 章で使う。https://www.postman.com/downloads/ |

PC 全体の Python を汚さないよう、`factory-replay` 専用の仮想環境（venv）にライブラリを入れる。

```powershell
cd factory-replay
python -m venv .venv
.\.venv\Scripts\Activate.ps1         # プロンプトの先頭に (.venv) と出れば OK
pip install -r requirements.txt      # boto3[crt]（aws login の認証情報を使うため crt 付き）
```

- `このシステムではスクリプトの実行が無効になっているため…` と出たら、次を一度だけ実行してから有効化し直す

  ```powershell
  Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
  ```

- `.venv` フォルダは Git 管理外。終わるときは `deactivate`

## 1. 毎回の準備

ターミナルを開くたびに実行する。

```powershell
cd factory-replay
.\.venv\Scripts\Activate.ps1
aws login
aws sts get-caller-identity          # 自分のアカウント・ユーザーが表示されれば OK
aws configure get region             # ap-northeast-1 であること（違う場合は各スクリプトに --region を付ける）
```

環境を作った後（3 章以降）は、続けて次の変数と関数を定義しておく。以降の手順はこれを使う。

```powershell
$owner = "<owner>"
$stack = "xcp-factory-$owner"
function stackout($key) {
  aws cloudformation describe-stacks --stack-name $stack --query "Stacks[0].Outputs[?OutputKey=='$key'].OutputValue" --output text
}
$bucket  = stackout BucketName
$cluster = stackout ClusterArn
$secret  = stackout SecretArn
$api     = stackout ApiUrl
function sql($q) {
  aws rds-data execute-statement --resource-arn $cluster --secret-arn $secret --database factory `
    --format-records-as JSON --query formattedRecords --output text --sql $q
}
```

- `sql "SELECT ..."` で DB に直接 SQL を投げられる（結果の時刻は UTC）
- `DatabaseResumingException` が出たら DB が一時停止から再開中。数十秒待って再実行する

## 3. AWS 環境を作る

```powershell
python aws/setup_aws.py --owner <owner>
```

初回は Aurora の作成に **10〜15 分** かかる。最後に次のように表示されれば成功。

```
Lambda コード用バケット xcp-factory-<owner>-artifacts-<アカウントID> を作成しました
スタック xcp-factory-<owner> を作成しています（初回は 10〜15 分ほどかかります）...
スタックの作成が完了しました
DB に接続しています（一時停止中なら再開まで数十秒かかります）...
テーブルと関数を作成しました: staging_readings, readings, replay_state, start_replay(), reset_replay()

スタック名 : xcp-factory-<owner>
バケット   : xcp-factory-<owner>-data-<アカウントID>
クラスター : arn:aws:rds:ap-northeast-1:<アカウントID>:cluster:xcp-factory-<owner>
HTTP API   : https://xxxxxxxx.lambda-url.ap-northeast-1.on.aws/
```

ここで 1 章の変数と関数を定義する。

### 確認 3-1：作成物

| 画面 | 確認すること |
|---|---|
| CloudFormation > スタック | `xcp-factory-<owner>` が `CREATE_COMPLETE` |
| RDS > データベース | クラスター `xcp-factory-<owner>`、インスタンスが `db.serverless` |
| RDS > クラスター > 設定 | 容量 0〜4 ACU、自動一時停止が有効、RDS Data API が有効 |
| S3 | `xcp-factory-<owner>-data-<アカウントID>` と `…-artifacts-<アカウントID>` |
| Lambda | `xcp-factory-<owner>-loader` / `-replayer` / `-api` |
| EventBridge > スケジュール | `xcp-factory-<owner>-replayer` が **無効**（CSV を置くまで動かない） |
| タグ | 各リソースに `Project=xcp-factory`, `Owner=<owner>` |

### 確認 3-2：テーブル

```powershell
sql "SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' ORDER BY 1"
sql "SELECT proname FROM pg_proc WHERE proname IN ('start_replay', 'reset_replay') ORDER BY 1"
sql "SELECT status, speed, total_rows FROM replay_state"
```

| SQL | 期待する結果 |
|---|---|
| テーブル | `readings`, `replay_state`, `staging_readings` |
| 関数 | `reset_replay`, `start_replay` |
| `replay_state` | `status: idle`、`speed: 60`、`total_rows: 0` |

### 確認 3-3：使っていない間は一時停止すること

最後の SQL から **5 分以上** 何もせずに待ち、CloudWatch > メトリクス > RDS で
クラスター `xcp-factory-<owner>` の `ServerlessDatabaseCapacity` が **0** になっていることを確認する。
0 の間は ACU の課金がかからない（ストレージ代のみ）。

## 4. ② アップロードして少しずつ反映させる

```powershell
aws s3 cp data/factory_sample.csv "s3://$bucket/incoming/"
```

`incoming/` の下に `.csv` を置くと自動で取り込みが始まる（それ以外の場所・拡張子は無視される）。

### 確認 4-1：取り込まれてリプレイが始まること（1 分以内）

```powershell
python tools/cli.py --owner $owner status
aws scheduler get-schedule --name "$stack-replayer" --query State --output text
```

| 項目 | 期待する結果 |
|---|---|
| 状態 | `running`（取り込み中は `loading`。`error` ならメッセージに理由） |
| CSV | `incoming/factory_sample.csv` |
| 速度 | `60.0` |
| 全行数 | `21600` |
| スケジュール | `ENABLED` |

### 確認 4-2：1 分ごとに少しずつ増えること

1 分おきに数回 `python tools/cli.py --owner $owner status` を実行する。

- 60 倍速なので **1 分ごとに約 900 行**（CSV の 1 時間分）ずつ「反映済み」が増え、「CSV 上の現在位置」が約 1 時間ずつ進む
- 「完了見込み」が約 24 分後を指す
- replayer のログでも確認できる（毎分 `{"msg": "反映", "moved": 900, ...}`）

  ```powershell
  aws logs tail "/aws/lambda/$stack-replayer" --since 10m
  ```

### 確認 4-3：最後まで流れたら止まること

1 日分は約 **24 分** で流れ終わる（待つ間に 5 章の Postman の準備をしておくとよい）。
待たずに先へ進みたい場合は、`python tools/cli.py --owner $owner reset --speed 720` で早送りできる（約 2 分。6 章で詳しく扱う）。

| 確認 | 期待する結果 |
|---|---|
| `python tools/cli.py --owner $owner status` | 状態 `done`、反映済み `21600`、進捗 `100.0` |
| `aws scheduler get-schedule --name "$stack-replayer" --query State --output text` | `DISABLED`（自動で止まる） |
| replayer のログ | `リプレイ完了。スケジュールを停止` |
| その 5 分以上後の `ServerlessDatabaseCapacity` | `0`（一時停止） |

## 5. ③ HTTP API で取得する

API は IAM 認証付きで、AWS の署名（SigV4）がないリクエストは 403 になる。4 章のリプレイが `done` になった状態で確認する。

### 5-1. Postman を準備する

1. Postman で **Import** → `factory-replay/postman/xcp-factory.postman_collection.json` を選ぶ（初回のみ）
2. Environment（API の URL と AWS の一時認証情報）を作ってインポートする

   ```powershell
   python tools/postman_env.py --owner $owner
   ```

   出力された `factory-replay/postman/xcp-factory-<owner>.postman_environment.json` を **Import** し、
   右上の Environment 選択で **xcp-factory-<owner>** を選ぶ

- 認証情報には有効期限がある（スクリプトが表示する）。切れると 403 になるので、`aws login` → スクリプト再実行 → 古い Environment を削除してインポートし直す
- このファイルには秘密情報が入る（Git 管理外）。人に渡したり、チームの共有ワークスペースにインポートしたりしない

### 確認 5-2：Postman で取得する

コレクションの 1〜10 を上から **Send** する（コレクションを右クリック → **Run collection** でまとめて実行し、テスト結果でも確認できる）。
11〜14 はリセットなので、ここでは送らない（6 章で使う）。

| # | リクエスト | 期待する結果 |
|---|---|---|
| 1 | status | 200。`status: done`、`reflected_rows: 21600`、`percent: 100.0`、`csv_end: 2026-10-01T23:59:00+09:00` |
| 2 | latest | 200。`count: 15`（5 設備のメトリクスごとの最新値）。`ts` は反映時刻、`source_ts` は CSV 上の時刻（どちらも +09:00） |
| 3 | latest（CNC-01） | 200。CNC-01 の 4 メトリクスだけ |
| 4 | readings 1 ページ目 | 200。CSV 上 14:00 からの `spindle_load` が 10 件（55 前後から上がっていく）。`next` に続きの位置が入る |
| 5 | readings 続き | 200。4 の続きの 10 件。Send を繰り返すとページが進み、最後は `next: null` |
| 6 | readings 直近 30 分 | 200。反映時刻で直近 30 分のデータ（`done` から 30 分以上たっていれば 0 件で正常） |
| 7 | summary 直近 60 分 | 200。設備ごとの件数・平均・最小・最大。PRESS・CNC には `status`（稼働率・停止分・異常停止分） |
| 8 | summary 6:00〜22:00 | 200。CNC-01 の `alarm_minutes: 9`（14:30 からのチョコ停）、PRESS-01 の `stop_minutes: 61`（昼休み 60 分 + 22:00 の 1 件）、`run_ratio: 0.937` |
| 9 | 入力エラー | 400。`limit は 1〜5000 で指定してください` |
| 10 | 署名なし | **403**（`Forbidden`）。IAM 認証が効いている |

### 確認 5-3：CLI で取得する

CLI は aws login の認証情報で自動的に署名するので、認証情報の貼り替えは不要。

```powershell
python tools/cli.py --owner $owner latest --equipment CNC-01
python tools/cli.py --owner $owner readings --equipment CNC-01 --metric spindle_load --source-from 2026-10-01T14:00 --source-to 2026-10-01T14:40
python tools/cli.py --owner $owner summary --source-from 2026-10-01T06:00 --source-to 2026-10-01T22:00
python tools/cli.py --owner $owner readings --all --csv > "$env:TEMP\all.csv"
(Get-Content "$env:TEMP\all.csv" | Measure-Object -Line).Lines
```

- `readings`（14:00〜14:40）は 41 件。14:30 付近で 90 を超えた後、0 になる（チョコ停）
- `summary` は CNC-01 が「稼働率 92.7%  停止 61 分  異常停止 9 分」
- 最後の行数が `21601`（ヘッダー + 21,600 行。ページを自動でたどって全件取れている）
- `--json` を付けると API の応答をそのまま表示する

### 確認 5-4：署名なしでは呼べないこと（コマンド）

```powershell
curl.exe -s -o NUL -w "%{http_code}`n" "${api}status"      # 403
```

## 6. ④ リセットする

リセットは `readings` を空にし、DB に取り込み済みの CSV（`staging_readings`）を先頭から再生し直す。
**S3 の CSV には触れない**（消えない・読み直さない）ので、大きい CSV でもすぐ再開できる。

| 操作 | Postman | CLI |
|---|---|---|
| 今の速度で最初から | 11. reset（今の速度で最初から） | `python tools/cli.py --owner $owner reset` |
| 720 倍速で最初から | 12. reset（720 倍速で最初から） | `python tools/cli.py --owner $owner reset --speed 720` |
| 空にして停止 | 13. reset（空にして停止） | `python tools/cli.py --owner $owner reset --stop` |
| 60 倍速に戻して最初から | 14. reset（60 倍速に戻す） | `python tools/cli.py --owner $owner reset --speed 60` |

### 確認 6-1：0 件から再び増えること（720 倍速）

1. **12（720 倍速）** を送る → 応答が `status: running`、`speed: 720`、`reflected_rows: 0`
2. 1 分おきに **1. status** を送る

| 経過 | 期待する結果 |
|---|---|
| 直後 | `reflected_rows: 0`、`estimated_finish` がおよそ 2 分後 |
| 約 1 分後 | `reflected_rows` が約 1 万件、`csv_position` が半日ほど進む |
| 約 2〜3 分後 | `status: done`、`reflected_rows: 21600` |

- `source_key` は変わらない（S3 は読み直していない）
- 完了後はスケジュールが `DISABLED` に戻る

### 確認 6-2：空にして停止できること

1. **13（空にして停止）** を送る → `status: idle`、`reflected_rows: 0`
2. **2. latest** が `count: 0`
3. 2〜3 分待っても **1. status** の `reflected_rows` は 0 のまま、スケジュールは `DISABLED`
4. **14（60 倍速に戻す）** を送ると `running` で再び増え始める（確認が終わったら流し終えるか、13 で止める）

## 7. （任意）異常系・大きいデータ

### 確認 7-1：壊れた CSV を置いたとき

```powershell
"this,is,not,valid" | Out-File -Encoding utf8 "$env:TEMP\bad.csv"
aws s3 cp "$env:TEMP\bad.csv" "s3://$bucket/incoming/bad.csv"
python tools/cli.py --owner $owner status
```

- 1 分以内に状態が `error`、メッセージが `incoming/bad.csv: CSV にデータ行がありません`
- CSV（`source_key`）は直前に取り込めた `incoming/factory_sample.csv` のまま。直前のデータも消えていない
- 元に戻すには `python tools/cli.py --owner $owner reset`（直前の CSV を最初から）か、正しい CSV をアップロードし直す

### 確認 7-2：大きい CSV（約 390 万行 / 230 MB）

```powershell
python tools/generate_csv.py --days 30 --interval 10s --out data/month.large.csv
aws s3 cp data/month.large.csv "s3://$bucket/incoming/"
python tools/cli.py --owner $owner status          # 数分おきに
```

- しばらく `loading` が続き（数分程度）、その後 `running`・全行数 `3888000` になる
- 取り込み中も `python tools/cli.py --owner $owner latest` は直前のデータを返す（取り込み完了時に空になって再スタート）
- 取り込み中に **11. reset** を送ると **409**（`CSV の取り込み中のためリセットできません…`）
- 60 倍速だと 30 日分は約 12 時間かかる。`running` になったら `reset --speed 720` で約 1 時間にできる
- 確認が終わったら `aws s3 cp data/factory_sample.csv "s3://$bucket/incoming/"` で小さいデータに戻すか、8 章で片付ける

## 8. 後片付け

検証を終えるときに実行する。DB の中身と S3 の CSV はすべて消える（スナップショットも残さない）。

```powershell
python aws/teardown_aws.py --owner $owner     # yes と入力すると削除開始（10 分ほど）
```

削除が終わると、課金されるリソースが残っていないかを自動で確認する。次のように出れば完了。

```
残っているリソースを確認しています（xcp-factory-<owner>）...
残っているリソースはありません（課金されるものは残っていません）
```

| 確認する対象 | 名前 |
|---|---|
| CloudFormation スタック | `xcp-factory-<owner>` |
| S3 バケット | `xcp-factory-<owner>-data-<アカウントID>`、`xcp-factory-<owner>-artifacts-<アカウントID>` |
| Aurora | クラスター `xcp-factory-<owner>`、削除後に残ったスナップショット・自動バックアップ |
| Lambda | `xcp-factory-<owner>-loader` / `-replayer` / `-api` |
| EventBridge スケジュール | `xcp-factory-<owner>-replayer` |
| CloudWatch Logs | `/aws/lambda/xcp-factory-<owner>-*` |
| VPC | Name タグ `xcp-factory-<owner>` |
| Secrets Manager | クラスターの RDS 管理シークレット |

- `残っています: …` と出たら、削除の反映待ちのことがある。数分後に `python aws/teardown_aws.py --owner $owner --check`（確認だけ）で再確認し、それでも残っていればコンソールから削除する
- スタックの作成に失敗して途中で止まった場合も、`teardown_aws.py` で残ったものを片付けられる

## 参考

### DB の中身をコンソールで見る（RDS クエリエディタ）

1. AWS コンソールで **RDS** → 左メニューの **クエリエディタ**
2. 接続画面で次を入力して **データベースに接続します**

   | 項目 | 入力値 |
   |---|---|
   | データベースインスタンスまたはクラスター | `xcp-factory-<owner>` |
   | データベースユーザー名 | **Secrets Manager ARN と接続する** |
   | Secrets Manager ARN | スタックの出力 `SecretArn`（CloudFormation > `xcp-factory-<owner>` > 出力） |
   | データベース名 | `factory` |

3. SQL を書いて **実行**

   ```sql
   SELECT * FROM replay_state;
   SELECT equipment_id, metric, value, ts AT TIME ZONE 'Asia/Tokyo' AS ts_jst, source_ts AT TIME ZONE 'Asia/Tokyo' AS src_jst
     FROM readings ORDER BY seq DESC LIMIT 20;
   ```

- 時刻は UTC で表示される（日本時間は `AT TIME ZONE 'Asia/Tokyo'`）。大量の行は `LIMIT` を付ける
- SQL を投げ続けている間は DB が一時停止しない（開いたままでも、実行しなければ 5 分で止まる）

### コードを変更したとき・作り直すとき

| やりたいこと | 手順 |
|---|---|
| Lambda・テンプレート・スキーマの変更を反映 | `python aws/setup_aws.py --owner $owner` を再実行（データは消えない。変更がなければ「スタックに変更はありません」） |
| Postman コレクションの変更を反映 | コレクションを Import し直す（同名は置き換え） |
| ゼロから作り直す | `teardown_aws.py` → `setup_aws.py` → CSV をアップロード。HTTP API の URL が変わるので `postman_env.py` で Environment も作り直す |

## うまくいかないとき

### 準備・ログイン

| 症状 | 原因と対処 |
|---|---|
| `Your session has expired` / `Unable to locate credentials` | `aws login` をやり直す |
| `MissingDependencyException: ... pip install "botocore[crt]"` | `pip install -r requirements.txt` をやり直す（`boto3[crt]` が入る） |
| `ModuleNotFoundError: No module named 'boto3'` | 仮想環境が有効になっていない。`.\.venv\Scripts\Activate.ps1`（初回なら 0 章から） |
| `--owner は英小文字で始まる…` | 英小文字で始め、英小文字・数字のみ 2〜16 文字にする |

### 環境の作成

| 症状 | 原因と対処 |
|---|---|
| `スタックの作成に失敗しました` | `aws cloudformation describe-events --stack-name xcp-factory-<owner>` で失敗したリソースと理由を確認。`teardown_aws.py` で片付けてから再実行する |
| 理由が `The maximum number of VPCs has been reached` | リージョンの VPC 上限（既定 5）。不要な VPC を消すか、Service Quotas で上限緩和を申請する |
| 理由に `already exists` | 同名のリソースが残っている。`teardown_aws.py` を実行してから再作成する |
| 理由に `MinCapacity` / `SecondsUntilAutoPause` の非対応 | 既定のエンジンバージョンが 0 ACU 非対応の可能性。テンプレートでバージョンを指定する必要があるので報告する |
| `DatabaseResumingException` が続く | 一時停止からの再開待ち。1 分ほど待って再実行する |

### 取り込み・反映

| 症状 | 原因と対処 |
|---|---|
| アップロードしても状態が変わらない | 置き場所が `incoming/` 直下で拡張子が `.csv` か確認。`aws logs tail "/aws/lambda/$stack-loader" --since 30m` で loader が動いたか見る |
| `error`：`unable to access credentials stored with the database instance` | DB の再開直後・スタック更新直後に、DB が S3 取り込み用ロールの認証情報をまだ取得できていない（一時的）。loader が 2 分ほど自動で再試行するが、それでも失敗したら数分待ってアップロードし直す |
| `error`（上記以外） | メッセージに「CSV 名: 理由」が入っている。ヘッダー `ts,line_id,equipment_id,metric,value,unit` 付き・時刻順の CSV か確認して置き直す |
| `running` なのに件数が増えない | スケジュールが `DISABLED` になっていないか確認（スタック更新で戻ることがある）。`reset` か CSV のアップロードで再開する |
| `loading` のまま変わらない | loader のログを確認。CSV を置き直すとやり直せる（60 分たつと自動で `error` になる） |

### API・Postman

| 症状 | 原因と対処 |
|---|---|
| 403：`The security token included in the request is expired` など | 一時認証情報の期限切れ。`aws login` → `postman_env.py` → Environment をインポートし直す |
| 403：`Forbidden` のみ | Environment が選ばれていない、またはコレクションの Authorization（AWS Signature・Service Name `lambda`）が変わっている |
| `is not authorized to perform: lambda:InvokeFunctionUrl` | 自分の IAM 権限が足りない。アカウント管理者に依頼する |
| 503：`DB が一時停止から再開中です` | 30 秒ほど待って再実行する |
| 503：`CSV の取り込み中のため…` | 大きい CSV の取り込み中。`running` になってから再実行する |
| 404：`POST /reset はありません` など | Lambda が古い。`setup_aws.py` を再実行する |

### リセット

| 症状 | 原因と対処 |
|---|---|
| 409：`CSV の取り込み中のためリセットできません` | 取り込み完了（`running`）を待ってから再実行する |
| 409：`CSV がまだ取り込まれていません` | 一度も CSV を取り込んでいない。先に `incoming/` に CSV をアップロードする |
