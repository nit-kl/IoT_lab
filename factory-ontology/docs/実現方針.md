# 工場データ × ナレッジグラフ × 担当者通知:実現方針

状態:**合意済み。ステップ 5 まで完了**。
改訂:2026-11-07。Auto-Ontology をやめ、AI を台本モックとし、オンプレ DB を Oracle に変更しました。

## 1. 目的と範囲

| 区分 | 内容 |
|---|---|
| **プロダクトの価値** | 役割ごとに、適切な情報を、適切な情報量で、適切なタイミングで届けること |
| **検証すること①** | データ収集から担当者への通知までの仕組みが、安全に、欠損や重複なく動くこと |
| **検証すること②** | 複雑な工場データをナレッジグラフで表現し、複数の関係をまたいで問い合わせできること |
| 今回は検証しないこと | AI が問題を発見できるか、分析の質(次の段階) |

| # | 要件 | 実現方法 | 本物 / モック |
|---|---|---|---|
| ① | オンプレ RDB に工場データが集約 | 手元 PC に Oracle AI Database Free を立て、基幹システム風の表を作る | データは模擬、DB は本物 |
| ② | クラウドへ吸い上げ | 抽出プログラムが差分を外向き HTTPS で S3 へ送る | 本物 |
| ③ | ナレッジグラフ構築 | 届いたデータを標準 RDF に変換し、グラフを更新する | 本物 |
| ④ | 適切な時に適切な人へ通知 | 検知、宛先の特定、SES 送信は本物。分析文だけ台本 | **文章のみモック** |

## 2. 全体像

```text
【オンプレ模擬:手元PC】               【AWS 東京:すべて使った分だけの課金】
 Oracle(工場DB)
   ↑ 模擬データ生成(筋書きどおり)
   ↓ 読み取り専用ユーザー
 抽出プログラム ──HTTPS(外向きのみ)─→ S3 raw/(変更不可の受信記録)
   ・許可した表/列だけ                      │ 新着
   ・個人名は送らない                       ▼
                                       EventBridge → SQS FIFO(新着の合図) ─失敗→ DLQ
                                            ▼
                                       Lambda グラフ更新(未処理のファイルを順に反映)
                                            ├─→ S3 kg/current.nq.gz(版管理)
                                            ▼          ▲ 読み取り
                                       Lambda 通知 ──┴─ SPARQL で検知・宛先特定・事実収集
                                        ▲   │ DynamoDB で重複送信を防止
         EventBridge Scheduler(日次/週次)┘   ├─ 台本モック(分析文)
                                             └─ SES → 担当者別メール

 手元のビューア ──S3 のグラフを読むだけ
```

常時稼働のサーバーはありません。データが届いたときだけ動くので、費用が小さく、攻撃を受ける面も狭くなります。

## 4. ナレッジグラフ

### 表現する複雑さ

模擬 RDB は 27 表とし、実際の基幹システムでよくある難しさを意図的に入れます。

| 複雑さの種類 | 例 | グラフでの表現 |
|---|---|---|
| 分かりにくい名前 | `T_EQP_ALM`、`KIKAI_CD`、コード値 | 変換定義で標準語彙に対応づけ |
| 階層 | 工場 > エリア > ライン > 設備 > 部位 | 標準の階層関係 |
| 自己参照 | 部品表(BOM) | 部品どうしの関係 |
| 多対多 | 製造指図 ↔ 材料ロット | ロットの追跡関係 |
| 期間つきの関係 | 部品の取付期間、当番表 | 関係そのものをイベントのノードにする |
| システム間の ID の不一致 | `PRS-03` と `PRESS3` が同じ設備 | 別名対応表で 1 ノードに統合し、元 ID は保持 |
| 欠損・不正データ | 未登録のコード、参照先なし | 検査で検出し、隔離または警告 |

### 含める範囲

| 区分 | 内容 |
|---|---|
| グラフに入れる | 組織、設備、部品、仕入先、ロット、製品、製造指図、生産実績、検査、アラーム、停止、保全、担当の役割、当番 |
| 入れない | **高頻度のセンサー値と時間ごとの電力量**。計測項目の定義と異常イベントだけをグラフに入れ、時系列の値は S3 に残す |
| 入れない | **個人名**。社員は社員番号で表す |

以前の測定どおり、センサー値まで入れると Lambda のメモリ上のグラフでは持ちません。模擬データ 14 日分の実測は約 1.6 万クワッド(3.3MB)で、1 日あたり約 1,100 クワッドです。**20 万トリプルに届くのは約 6 か月分**なので、ステップ 4 で古い生産実績の保持期間を決めます。

### 複雑さの検証基準

「表現できた」を次の問い合わせで判定します。

| # | 問い | たどる関係 |
|---|---|---|
| 1 | このアラームの設備に、今取り付いている部品の仕入先はどこか | アラーム → 設備 → 取付 → 部品 → ロット → 仕入先 |
| 2 | 同じ仕入先ロットの部品を使う設備は、他にどれか | ロット → 部品 → 取付 → 設備 |
| 3 | 不良ロットの影響を受けた製造指図と製品はどれか | ロット → 指図 → 製品 → 検査 |
| 4 | この設備の異常時に、当番だった保全担当は誰か | 設備 → エリア → 当番表 → 役割(時刻で絞る) |
| 5 | 同じ型式の設備で、過去に同じ事象と対処はあったか | 設備 → 型式 → 設備 → 保全履歴 |
| 6 | 別システムの ID で検索しても同じ設備にたどり着くか | 別名 → 設備 |

あわせて次も確認します。
- 全行が変換され、RDB の件数とグラフの件数が一致すること
- SHACL 違反がゼロで、埋め込んだ不正データは検出されること
- ビューアでたどれること
- 問い合わせの応答時間

### 更新の方式

- 変換規則は宣言的な定義ファイル(`graph/mapping/mapping.toml`)に集約します。全列について、使うか、使わない理由があることをテストで確認します。
- 元の 1 行を 1 つの名前付きグラフに入れます。Lambda は現在のグラフを読み、変更された行のグラフを差し替えて、S3 へ書き戻します。論理削除は、そのグラフを消すだけです。
- S3 の通知は FIFO キューへ直接送れないので、EventBridge を挟みます。メッセージは「新着あり」の合図とし、Lambda が未処理のファイルをキーの順に全部処理します。同時に 1 つしか動かず、再試行しても結果は変わりません。
- 処理位置はグラフのファイルのメタデータに持ちます。グラフと処理位置は必ず同時に更新されます。
- 読めないファイルは `kg/rejected/` に記録して飛ばし、処理位置は読めたファイルでだけ進めます。
- 抽出の読み取り位置を消して全件を送り直すと、グラフは作り直されます。
- 生産実績は 90 日で消します。受信データ `raw/` も 90 日で消えるので、全件の再構築は 90 日以内のデータに限られます。
- S3 の版管理で前の状態へ戻せます(直近の数版)。
- 全件の SHACL 検証は Python では時間がかかるので、テストと手動実行で行います。

**制約**:更新のたびに全体を読み書きするので、大規模には向きません。100 万トリプルを超える場合は Neptune 等へ移します(TTL と SPARQL はそのまま使えます)。

## 5. 収集から通知までの流れと、検証する異常系

### 収集

- `updated_at` の続きから差分を取り、少し重ねて読みます。遅れてコミットされた行も拾うためで、重複はグラフ側で無害になります。
- 取得位置はオンプレ側に保存し、S3 への送信成功後に進めます。
- 1 回分を gzip JSONL 1 ファイルにまとめ、変更がなければ送りません。

### 通知

| 役割 | 知りたいこと | 情報の範囲 | 情報量 | タイミング |
|---|---|---|---|---|
| 工場長 | 判断が必要なことはあるか | 工場全体 | 3 行 + 要点 | 毎朝、最重大のみ即時 |
| KPI 責任者 | 目標に対してどうか | OEE、歩留り、原単位 | 数値 + 前週比 | 毎朝、週次 |
| ライン責任者 | 自分のラインは今どうか | 担当ラインのみ | 中 | シフト開始前、ラインの異常時 |
| 保全当番 | 何が起き、どう直すか | 担当エリアの設備 | 詳細 | 即時、当番の時間のみ |
| 品質保証 | どこまで影響するか | ロットと影響範囲 | 詳細 | 品質異常の発生時、毎朝 |
| 生産管理 | 納期に響くか | 製造指図と納期 | 短い | 納期に影響するときのみ |

- 宛先の役割と担当範囲は**グラフで解決**します(例:その時刻の当番、停止で影響を受ける指図の担当)。
- 送信先は `you@example.com` の 1 つにまとめ、件名の `[役割名]` で区別します。役割ごとの宛先は `setup_aws.py` の設定(Lambda の環境変数)で切り替えられます。
- 送らない判断も理由つきでログに残します。
- 同じ設備・同じ事象は DynamoDB で 1 回に束ね、1 日の送信数にも上限を設けます。
- **未解決時の上位通知**:保全当番が一定時間内に対応済みとしなければ、ライン責任者、工場長の順に通知します(既定は 5 分、10 分)。対応済みは、メール内のリンクを開いて確認画面のボタンを押すと記録します。リンクは有効期限つきの署名で保護します。開くだけで記録しないのは、メールの安全確認ソフトがリンクを自動で開くためです。
- **成果の測定**:全員に一斉送信した場合と比べた通知の削減率を、日次で記録します。

### 台本モック

- レポート生成は「文脈を入れると文章が返る」1 つの差し替え口にまとめ、次の段階で本物の LLM に置き換えます。
- 検知規則ごとに台本を持ちます。設備名や件数などの事実はグラフの結果から差し込み、分析と提案の文は固定です。
- 本物の AI と誤解されないよう、メールの末尾に「デモ用の台本です」と 1 行入れます。

### 検証する異常系

| 状況 | 期待する動き |
|---|---|
| PC を止めて翌日再開 | 欠損なく追いつく |
| 同じファイルを再送 | 重複ノードも重複メールも出ない |
| 順番どおりでない到着、遅延コミット | 最終状態が RDB と一致する |
| 行の更新・論理削除 | グラフに反映される |
| 不正データの混入 | 隔離して他の処理は続き、管理者に警告が届く |
| Lambda の失敗 | 再試行後に DLQ へ入り、管理者に警告が届く |
| 当番が未登録 | 上位の役割へ送る |
| 保全当番が未対応のまま時間切れ | ライン責任者、工場長の順に通知し、対応済みになれば止まる |
| SES の失敗 | 再試行し、送信記録が二重にならない |

## 6. セキュリティ

| 対象 | 対策 |
|---|---|
| オンプレ境界 | 受信ポートなし、HTTPS の外向きのみ。Oracle は 127.0.0.1 限定で公開し、抽出は読み取り専用ユーザー |
| 持ち出すデータ | 許可リスト(`onprem/extractor/policy.toml`)の表・列だけを読んで送る。個人名の列は対象外 |
| オンプレの認証 | IAM Roles Anywhere(証明書から短命の認証情報を取得)。権限は `raw/` への新規書き込みのみで、上書き、読み取り、一覧、削除はできない |
| S3 | 公開ブロック、SSE-S3、TLS 必須、バージョニング |
| Lambda | 関数ごとの最小権限。Function URL は IAM 認証、SPARQL は読み取り専用。対応済み記録の URL だけは有効期限つき署名で保護 |
| SES | 送信元を IAM 条件で限定し、1 日の送信数に上限(50 通) |
| 自由記述 | 保全メモはデータとして扱い、メールでは HTML エスケープ |
| 費用の暴走 | 日次の送信上限、定時レポートは既定で停止、データが届いていなければ送らない |

## 7. 構成の判断

| 論点 | 採用 | 見送った案 |
|---|---|---|
| 吸い上げ | 自作の抽出プログラム | **DMS** は常時費用と VPN 等が要る。**Glue** はオンプレへの到達経路が要る |
| グラフ DB | Lambda + Oxigraph(S3 上の N-Quads) | **Neptune** は以前の確認で月 $100 以上 |
| 実行基盤 | Lambda | Auto-Ontology がなくなり、EC2 は不要 |
| グラフの読み取り | S3 のファイルを直接読む | SPARQL 用の Lambda は作らない。ビューアは S3 を読むだけで足り、通知の Lambda はグラフを自分で読み込む。部品と攻撃面が減る |
| 分析用 RDB | 置かない(通知はグラフ、生データは S3) | Aurora 等は不要。センサー値の集計が必要になれば Athena を追加 |
| 重複防止 | DynamoDB(オンデマンド) | SQS だけでは送信の重複を防げない |

## 8. 費用と進め方

### 月額の概算

| 項目 | 月額の目安 |
|---|---|
| Lambda(実測 1 回約 0.4 秒、1GB。60 秒間隔でも月 2 万 GB 秒未満) | 約 $0.3 以下 |
| S3 / SQS / DynamoDB / SES / Scheduler | 約 $0.5 以下 |
| Parameter Store 標準パラメータ / IAM Roles Anywhere | $0 |
| **合計** | **約 $1〜2(150〜300 円程度)** |

単価は未検証の概算です。AWS にログインできたら Pricing API で確認し、ステップ 6 で実費に置き換えます。

### 手順(各ステップの確認後に次へ)

| ステップ | 内容 | 完了の判定 | AWS 費用 |
|---|---|---|---|
| 1 | オンプレ模擬:Oracle、表設計、データ生成、筋書き | 27 表が Oracle に入り、§4 の複雑さを含む | なし |
| 2 | オントロジーと変換:手元でグラフ構築、ビューア | **§4 の問い 1〜6 が通る** | なし |
| 3 | 吸い上げ:Oracle の連続更新、抽出、S3、Roles Anywhere | 差分転送、許可外の列が出ない | 少額 |
| 4 | グラフ自動更新 | S3 のグラフが Oracle からの再構築と完全に一致 | 少額 |
| 5 | 検知、宛先特定、台本モック、SES、上位通知、デモの操作 | 役割ごとに適切なメールが届く | 少額 |
| 6 | 異常系の試験、手順書、費用測定、撤去 | §5 の表をすべて確認、残存リソースなし | 少額 |

グラフ表現を先に手元で固めるので、AWS を使う前にモデルの妥当性を確認できます。

**模擬データの筋書き(案)**:
- 軸受の摩耗 → 振動の異常 → 不良率の上昇 → ライン停止
- 特定の仕入先ロットによる不良の集中
- 待機中の電力の無駄
- 夜勤シフトでの段取り替えの長時間化

## 10. フォルダ構成

```text

  docs/            方針書、手順書
  onprem/          オンプレ側で動くもの
    db/            Oracle の表定義

    extractor/     差分の抽出と送信、許可リスト
    tests/
  graph/           オントロジー、変換定義、問い合わせ(ステップ 2)

```

各フォルダは、ステップごとに必要になった時点で作ります。
